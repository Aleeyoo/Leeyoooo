# GitHub 存得下文档，存不下对话

最近 @DashHuang  这篇《为什么要用 GitHub 作为 AI Native 时代的知识协作底座》传得很广。他的主张我基本同意：公司里需要长期沉淀的知识——工作日志、文档、技术方案，越来越适合放进 GitHub。Git 的版本、diff、blame，让知识带上了时间线和责任人；AI Agent 又天然熟悉这套结构。对"被人写下来的知识"来说，这是个好底座。

但读完，我想到的是另一半。**团队中有另一类知识，GitHub 这种偏静态的知识库维护好它会很困难，因为传统上它没法时刻被结构化存下来。**

它活在内部群聊，以及对外的对话里，开发的对话是知识、运营的回答也是知识，更具代表性的是社区Moderator的回复，同样也是知识，它们说完就沉进聊天记录，没有人会把它们整理成 Markdown、提一个 PR。这类知识边产生、边过期，却从不被沉淀。

Dash 的方案是Agent时代解决知识写下来之后放哪的最佳方案之一，这篇想更往前一步：**那些根本没被写下来的知识，Agent 该怎么用？**

## 〇、谁适合阅读这篇文章？

这篇主要写给这几类人：

- 正在评估AI Moderator、AI 运营、AI知识库这类产品，想要一把能衡量它们的尺子
- 读过 Dash 那篇讲 GitHub 的文章，认同它，但隐约觉得还有一类知识它没覆盖
- 想把 RAG 和 Agent 记忆这两件事彻底搞清楚：它们各自怎么用、在哪失效
如果你本来就在做 RAG 基础设施或知识管理产品，这篇内容会比较浅，因为这套工程你应该已经烂熟于心。

## 一、知识库这个词，其实是个工程制品

先把知识库拆开，因为大家用这个词的时候，含义并不一样。

工程上，知识库是个很具体的东西：一堆文档，切成片段（chunk），算成向量，塞进一个能检索的索引。

它有两笔成本，一笔显性，一笔隐性。

显性那笔在"建"：文档怎么切、切多大、用什么模型 embedding、配什么索引。这是实打实的工程。

隐性那笔在"养"。知识库是一张静态快照，业务却是动的——

> 知识会被实时更新，旧答案随时过期。你需要定义"足够新""足够可信"的标准。
大多数知识库面临的困境，是第二种。建库是一次性的痛，养库是每天的痛。我见过的知识库，很少会建不出来，但多数建完之后没人管。

> 知识库不是一次性工程。它更像一栋要持续打扫的房子——没人维护，很快就不能住。
## 二、社区知识库：把难度调到最高

我用社区做样本，因为它是知识库的地狱难度。

企业内网的文档库，至少占三个便宜：知识是结构化的、更新是低频的、有专人负责。社区知识库，一个都不占。

![](https://pbs.twimg.com/media/HI4bK43bsAA59CP.jpg)

社区知识最别扭的一点是：它一直在被生产，却从不被沉淀。运营在群里随口回一句"这功能下周上"，是知识；三天后改口"延期到月底"，也是知识。两句话说完都沉进聊天记录，没人会把它们整理进任何库，更不会有人为它开一个 PR。GitHub 那套版本管理，恰恰够不到这里。

## 三、第一条路：RAG，把库查得更准

第一条路承认知识库存在，目标很纯粹：既然有库，就查准它。

这条路有个常被低估的事实：demo 的 RAG 和生产的 RAG，不是一个东西。

大多数 demo 用"单次向量检索 + 默认 chunking"，这套在真实查询上的准确率只有 40-60%。要把准确率提升到生产水平，得逐层加工程：

![](https://pbs.twimg.com/media/HI4b6wOa4AAVSIf.jpg)

每一层都都对应一个 demo 项目会犯的真实错误。效果也也明显，Anthropic提出的 contextual retrieval 中，基准测试里把检索失败率降了 49%，加上 rerank 到 67%。

> RAG 没有捷径。你以为绕过的每一层工程，最后都会变成一次答错。
如果知识相对稳定，这条路走得通。但社区知识恰恰不稳定，这是它难的地方。

提出 contextual retrieval 的人自己写明了适用范围：它最适合"稳定的、被高频查询的文档集"。但是如果每个 chunk 配一段摘要要花一次 LLM 调用，文档天天变就得天天重算，不仅成本撑不住，用户体验也会直线下降。

于是 RAG 在社区场景真正的难点，不是查得准，是另外两个：

一是**新鲜度/freshness**——查回来的东西，还没过期吗？这个问题没有银弹，最终目标是为每条知识定义"足够新"的标准。

二是**知识冲突**——旧片段说"A是正确的"，新片段说"B是正确的"，两条都在索引里。检索器只懂相似度，不懂时间，也不懂真伪，它分不清谁对。

> 在社区场景，RAG 难的不是"检索得准"，是"检索回来的还没过期"。
这两个问题本质不在检索，而在于知识的生命周期管理。

## 四、第二条路：记忆，不维护库，沉淀状态

第二条路换了思路：干脆不要知识库这个静态制品。知识不靠人建、人养，而是从交互流里自然派生。

谈这条路先要有记忆的分类，借人脑的划分：

![](https://pbs.twimg.com/media/HI4b9PVbgAE70gR.jpg)

传统知识库只覆盖最后一行 Semantic，而且用最笨的方式：让人手写。

第二条路赌的是：Episodic 里藏着大量 Semantic。运营每一次回答、每一次纠错，都在生产知识。你不必让他另外写库，只要把这些交互沉淀下来。

> 与其雇人维护一个知识库，不如让知识从每一次真实对话里自己长出来。
这两年情景记忆已经变成了一个专门的工程方向，名字就叫 Agent memory，几个有代表性的做法值得知道，因为它们之间的分歧，恰恰是这条路最关键的地方：

- **MemGPT / Letta**：把上下文窗口当操作系统的虚拟内存来管。记忆分三层——核心记忆常驻窗口（像 RAM）、召回记忆是窗口外可搜索的对话历史（像磁盘缓存）、归档记忆是长期冷存储，Agent 靠工具调用去读写。它甚至让 Agent 自己编辑自己的记忆块
- **Mem0**：一个能挂到任何 Agent 框架上的"记忆层"，自动从对话里抽取、压缩记忆
- **Zep**：不建向量索引，建一张"时序知识图谱"，记的不只是事实，还有每条事实从何时为真、何时被推翻
![](https://pbs.twimg.com/media/HI4fG9EaYAA9m37.jpg)

接下来面临一个新的问题——有损压缩。

交互流会无限变长，上下文窗口有限，迟早要面对"装不下了怎么办"。主流答案是压缩：把旧消息压成摘要。方便，但本质是有损的，摘要替换掉了原始事实，事后你拿不回当时到底发生了什么。

而比"压不压缩"更难解决的是冲突问题：**两条知识冲突时，系统该怎么办？**

一派是改写。以 Mem0 为代表——新事实进来，和旧的冲突，它倾向于直接改掉旧的，而不是再堆一条。好处是记忆始终精简；代价是历史没了，事后你没法回答"当时为什么那么判断"。

另一派是只追加、不改写。旧事实不删，只标记成"已被取代"；要当前状态，就把日志重放一遍。这一派主张 Agent 的底座不该是"会话历史 + 各种记忆技巧"，而该是一条只追加、不修改的日志：

> 多层摘要、反复压缩和复杂启发式规则在短期内可能有效，但长期会引入噪声、不确定性和不可解释性。你会越来越难区分哪些是事实，哪些是模型生成的概括，哪些是压缩后的残留误差。
![](https://pbs.twimg.com/media/HI4jZlEbsAAlBVx.jpg)

这条"只追加、按需重算状态"的日志，其实是软件工程里一个有年头的成熟模式：event sourcing/事件溯源。Zep 那张时序知识图谱是同一个思路的典型实现——给每条事实都钉上时间。于是上述知识冲突的难题忽然有了解：检索器不再需要在两条矛盾的片段之间猜谁对，因为每条事实自己就带着“什么时候”为真的结果。

这里值得把开头那条线接上。Dash 推崇 GitHub，底层推崇的其实是 Git 的历史观——只追加、不可改、可追溯；Git 的 commit 历史本身就是一种事件溯源。psiace 给 Agent 记忆开的药方，是同一个直觉的另一种落法。区别只在知识的形态：被写下来的知识，这个直觉落成一个 Git 仓库；对话里流动的知识，它得落成一条只追加的记忆日志。同一个原则，两种载体。

把几种做法摆一起：

![](https://pbs.twimg.com/media/HI4cAENbAAAdX4e.jpg)

这张表是第二条路的分水岭。一个记忆系统可不可信，不看它"记得多"，看它有没有保住事实本身。

> "更可靠的交互"会胜过"更聪明的记忆"。—— @repsiace 
## 五、于是问题来了：这套东西，你要自己搭吗

两条路摆完，有一点应该清楚了：不管走哪条，背后都是一长串专业工程。

RAG 那条，是 chunking、hybrid 检索、rerank、contextual retrieval，外加一套评估。记忆那条，是记忆分层、压缩策略的取舍、改写还是追加、要不要上时序图谱。而这还只是轮廓。

所以真正该问的，不是"我选哪条路"，是另一个问题：

> 这套东西，你要自己搭吗？
答案取决于你是谁。

如果 RAG 基础设施就是你的核心业务——你在做 AI 搜索、做知识管理产品——那你当然自己搭，这是你的护城河。

但如果你只是在运营一个社区呢？你的核心能力是社区——把用户留住、把氛围做起来、把问题接住。RAG 的 rerank 调参、记忆系统的改写策略，对你不是护城河，是绕路。你自己搭一套，大概率搭得比专门做这件事的人差，还把时间花错了地方。

这就是"开箱即用"这类产品存在的理由，我们以近期宣布融资的 @LuciusHQ 为例：

**一，它能够自己从对话里抽知识，而不是仅仅提供一个“记忆库” ** 按 Lucius 自己的说法：你只在一开始告诉它一次社区的特别之处——产品口径、品牌语气、用户分层、KYC 窗口、什么必须转人工——之后政策改了、定价变了，它"听着、把变化抽出来、把知识更新掉"。养库的人从你变成了它。

**二，存的得是"决策"，而非"文档" **RAG 检索文档，分不清两条矛盾片段谁对。一个做对了的产品，沉淀下来的不该是原始文档，而该是一条结构化的判断——这是什么场景、边界在哪、该怎么处理，而且只追加、带时间。这样冲突和过期在数据层就化解了，不丢给检索器去猜。Lucius 的设计里有个细节正好踩在这上面：它答不了的问题转给人，人回答完，它不是把这句话原样存回库，而是把这次处理抽成一条可复用的判断。传统 RAG 复用的是"文档"，它复用的是一次判断或者决策。

**三，分得清什么时候自己做、什么时候引入HITL **这是产品的边界设计，也是出事和不出事的分界。权限之内它能够自己处理；到了边界，它把决定连同完整对话、几个可能的选项、一份草拟好的回复一起交给决策人。"边界 + 草稿"，比"答不上来就 @ 一个人"细得多——前者你点一下就行，后者你还得自己从头读起。

**四，得跨平台记住同一个人 ** 一个用户在 Discord 提过的事，换到 Telegram 接着问，应该命中同一份记忆。如果做不到这点，它就只是个绑在单一平台上的机器人。

这四条，没有一条是调个 prompt 能糊出来的。它们前面那一长串工程实践（chunking、rerank、事件溯源、时序图谱），只不过是换成了你不用碰的形态。它省的也不只是建库那一次：知识库真正的成本在维护，开箱即用省掉的，是那个每天都要付的成本，外加不用为此专门招一个懂 RAG 的人。

## 六、就算用现成的，也别跳过验证

决定不自己搭，不等于可以不验。

这类产品最爱报的数字是"自解决率"。Lucius 公开的案例里有一个常被引用的：某个工具的社区接入后，自解决率从 29% 升到 88%。

这个数字，我建议打个折看。两个原因。一是它是厂商自己报的口径。二，更要紧——自解决率本身就是个粗指标。它只说"多少问题没惊动人类"，不说"答得对不对"。一个 AI 要是把人糊弄到不想再问，自解决率也会很好看。

要真评估一个"AI Moderator"，得看 RAG 那套更硬的指标：

![](https://pbs.twimg.com/media/HI4cF0rbEAAdPAS.jpg)

faithfulness 在这里最要命。AI 客服把"下个月上线"说成"已经上线"，那不是答错，是事故。RAGAS、DeepEval 这类开源框架已经把这种打分自动化了。

还得多说一句，免得你转头又去信另一种数字：连记忆这个领域的公开基准，也别尽信。常用的 LOCOMO，单段对话只有一两万 token——本来就塞得进现在的上下文窗口。有人做过对照：什么记忆系统都不用、直接把整段对话塞进去，得分反而比挂了 Mem0 还高；Letta 自己的研究也发现，让 Agent 用最朴素的文件系统操作，比用花哨的图记忆还好。基准尚且如此，厂商案例页就更得打折。

因此，别光看官网数字，也别看榜。开箱即用的好处之一，恰恰是验证成本也低——这类产品多数能免费试一阵。接进一个你自己的群，拿上面那几个指标实测一遍，比任何案例页都准。

## 写在最后

回到开头那条分界线。被写下来的知识，GitHub 是一个不错选择；静态知识库无法解决的那一类问题的特点是边产生、边过期、从不被沉淀：要么把它检索得准确，要么让它从每一次交互里自己沉淀成事实。前者是 RAG，后者是记忆。

但更想说的其实是另一句：把 RAG 和记忆这两条路讲得这么重，恰恰是为了让你看清，这套东西，多数人不必自己搭。

> Agent 不需要"知识库"。而这套替代它的工程，多数团队也不必自己搭——值得的是把时间花回你真正的护城河上。
所以，如果你正是这类人——在运营一个社区，知识天天变，但你不想、也不该为了 RAG 和记忆这套工程单独招一个人、立一个项。
