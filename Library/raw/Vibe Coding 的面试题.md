## 第一题：vibe coding 质量怎么把控，bug怎么测试？

面试官担心的是 AI 生成的代码逻辑不严密或存在安全隐患。你可以从以下几个维度回答：

**1\. 质量把控的核心逻辑：从“编写者”转变为“评审者”**

**架构先行 (Architecture First)：** 在让 AI 写代码前，先要求它输出技术设计文档或 README。明确技术栈（如 Godot、Next.js）、模块边界和数据流向。这相当于给 AI 套上了“紧箍咒”。

**分步迭代 (Iterative Refinement)：** 不要一次性让 AI 写 1000 行代码。坚持“一个任务、一个 Commit”的原则。每完成一个小功能（如：角色移动逻辑），立即进行代码审计（Code Review）。

或者下面这个是一个意思

**模块化拆解**： 我不会让 AI 直接写一个巨大的功能，而是将其拆解为符合设计模式（如工厂模式、观察者模式）的微小模块，确保每个模块逻辑单一、可控。

**Prompt 约束**： 在 Prompt 中明确性能约束（如：‘使用 O(n) 时间复杂度’、‘避免不必要的重绘’）。

**深度 Review**： AI 产出的每一行代码我都会进行人工 Review。我会关注其闭包引用、内存泄漏风险以及是否符合目标平台的最佳实践”

**代码审计清单：** 强调你会重点检查 AI 容易犯错的地方，比如：

- **硬编码 (Hardcoding)：** 检查 API 密钥或敏感信息是否被泄露。
- **冗余逻辑：** AI 经常会重复生成相似的代码块。
- **边缘情况处理：** AI 倾向于写“快乐路径 (Happy Path)”，你需要强制它增加错误捕获和空值检查。

AI 确实可能产生幻觉，所以我建立了一套 测试驱动+AI 辅助 的验证流程。

**Bug 测试：AI 时代的“防御性编程”**

- **测试驱动开发 (TDD) 的复兴：** 告诉面试官，在生成业务代码前，你会先让 AI 生成 **Unit Tests (单元测试)**。只有通过了测试的代码才能被合并。
- **层级化测试体系： 自动化测试：** 利用 AI 快速编写 Playwright 或 Jest 脚本，覆盖关键路径。 **冒烟测试：** 每次生成代码后，利用 CI/CD 自动运行 lint 检查和类型检查（如 TypeScript）。 **探索性“感知”测试 (Vibe Testing)：** 关注 UI/UX 的直观感受（如：动画是否掉帧、交互是否自然），这是 AI 无法完全替代人类直觉的部分。
- **AI 联动 Debug**： 遇到 Bug 时，我会将报错日志、调用栈和相关上下文喂给 AI，利用它的多维推断能力定位边界条件错误，但我会手动验证修复方案的合理性。
- **边缘用例覆盖**： 专门利用 AI 生成‘破坏性测试用例’（Edge Cases），模拟用户极端操作，弥补人工思考的盲区。”
- **网友回答：**
- 1\. 一个terminal 负责专门编写基本功能单元的时候做好单元测试每个函数都带好单元测试 一边写功能一边写单元测试

2\. 另一个terminal 写功能的集成测试

3.再开一个写服务外部的api调用测试

4.开一个写性能测试 熟练了以后skill串起来

Vibe Coding 并不意味着对代码细节的妥协。我的做法是将 AI 作为‘超级执行单元’，而我承担‘架构设计’和‘代码审计’的角色。

我把 Vibe Coding 看作是『意图的委托』**。我的角色从 Coder 变成了 Code Owner。我通过**提示词工程 (Prompt Engineering) 来约束输入，通过**自动化测试套件**来验证输出。对于每一行 AI 生成的代码，我都会进行 **Human-in-the-loop (人工审查)**，确保代码的长期可维护性，而不是堆砌临时的功能碎片。

## 一段为了解决自己某个麻烦而写的自动化脚本

**项目描述：**每次上传ios 应用图片我觉得很麻烦，于是自己做了一个工具批量生成。只需要上传图片，勾选几下就能下载。

**项目描述：**平时看视频或听播客时，看到好的台词或画面想存成剧本素材，但截图、打字记录太慢。

一个 iOS或桌面端的自动化脚本。

- **功能：** 监听系统剪贴板或指定文件夹。当你截屏或录音后，脚本自动调用 OCR 识别文字，并利用 AI 总结成“编剧灵感卡片”，自动同步到 Notion 或 Obsidian。
- **面试亮点：** “我需要一个高度自定义的灵感库，市面的产品太臃肿。我用 Vibe Coding 在一个周末就完成了核心逻辑。这里面涉及了移动端异步处理和多模态 API 的调用，解决了我个人素材管理的大麻烦。”

## 让你用AI写一个面试助手ai其实就是作弊工具，你会怎么写，你的思路？

这是一个非常有意思且带有“挑衅性”的面试题。面试官其实是在考查你的**技术底线、工程思维**以及**对 AI 局限性的认知**。

## 1\. 定义产品定位（避开“作弊”字眼）

**核心逻辑：** 它不是替代思考，而是**消除信息差**和**降低认知负荷**。

## 2\. 技术实现思路（体现深度）

怎么理解深度，深度就是你思考的多和全面，不要被文字误解了，这个世界思考最全面的就是AI，自己思考肯定会宕机，被骂没有深度咱就承认。多向AI请教。

音频流处理与低延迟转译

- **技术点：** 使用 **WebSocket** 建立双向通信，利用 **Whisper API** 或 **Azure Speech-to-Text** 进行流式音频转文字。
- **挑战：** 延迟。
- **解决方案：** 采用“滑动窗口”机制，每 2-3 秒切片处理音频，确保文字几乎同步出现在屏幕上。

知识库挂载 (RAG 架构)

- **技术点：** 将你个人的 GitHub 项目、简历细节、甚至是常用的算法模板向量化，存储在 **Vector Database**（如 Pinecone 或 Milvus）中。
- **优势：** 当面试官问到“你那个 Godot 游戏的视差滚动是怎么实现的”时，AI 提取的不是网上的通俗答案，而是你代码库里的具体实现细节。

**UI/UX 设计（隐蔽性与易读性）**

**设计： 使用透明置顶窗口（Overlay），或者将建议答案以“关键词/提纲”而非“长篇大论”的形式呈现。**

基本就是这样，我觉得我还是需要一个ai面试工具的，不然不好过。

其实工作回答，他们特别喜欢流程化，你做的越规范越是提取什么东西抽象模块什么东西，他们会越喜欢你。解决问题，分析问题，工程化其实就是流程。怎么让流程运转的高效稳健，以上便是工作的最核心部分。他们喜欢机器，同时希望你像一个机器人一样没有情绪只有处理问题规范问题报告问题总结问题。

**spec markdown**

**spec markdown** 指的是用 Markdown 格式写的「规格说明文件」（specification docs）。 在 Agent-first 开发模式里，项目启动时仓库不放一行代码，只放一堆 .md 文件，把产品需求、功能细节、API 接口、UI 逻辑等全写清楚。AI Agent 再根据这些 spec 自动生成、迭代代码。

## 封装skill

我理解的 Skill 不仅仅是一个简单的插件，而是将 **领域知识（Domain Knowledge）** 转化为 AI 可调用的 **确定性工具**。在我的工作流中，我更倾向于根据特定的业务需求去‘封装’私有工具，而不是盲目下载通用插件。

我经常用cc官网的 frontend-design。这样写起来的UI风格会友好很多。

[https://github.com/anthropics/skills/tree/main/skills/frontend-design](https://github.com/anthropics/skills/tree/main/skills/frontend-design)

## 1\. 为什么要封装这个 Skill？（业务痛点）

“在短剧创作中，大模型生成的脚本往往‘网感’不稳定，或者容易触碰平台的审核红线（如过度暴力、违规题材）。如果只靠 Prompt 提示词去约束，AI 经常会‘幻觉’或者遗忘规则。为了解决这个问题，我不再通过对话框‘教’它，而是直接给它**封装了一个硬性的 Skill（工具）**。”

## 2\. 技术实现：Function Calling 与 API 接入

“我这个 Skill 的底层是基于 **Function Calling** 实现的。我编写了一个 Python 后端服务，主要做了三件事：

- **规则实时化**：通过 API 挂载了一个动态更新的‘短剧平台审核标准库’，确保 AI 调用的不是过时的知识。
- **确定性检测**：定义了一个 check\_compliance\_and\_vibe 函数。当 AI 生成剧本大纲后，系统会自动触发这个函数，将文本传给我的后端。
- **敏感词过滤**：利用 Aho-Corasick 算法实现的高效过滤引擎，对剧本进行逐字扫描，这比大模型模糊匹配要精准得多。”

## 3\. 输出稳定性：Structured Output（结构化输出）

“为了保证 Skill 返回的结果能被 Agent 直接理解并执行，我强制要求 Skill 返回 **Structured Output（JSON 格式）**。 例如，返回的数据结构包含：

- is\_passed: Boolean（是否过审）
- violation\_segments: Array（违规片段及原因）
- vibe\_score: Integer（网感评分，基于爆点频率计算）

这样，Agent 拿到这个结构化结果后，如果 is\_passed 为 false，它会自动进入重写逻辑，形成一个闭环。”

## 关于 Agentic Workflow（智能体工作流）

> “这个 Skill 不是孤立的。它是我的 **Agentic Workflow** 中的关键节点。我会设置一个‘反思循环’：编剧 Agent 生成 -> 审查 Skill 校验 -> 修正 Agent 调优。这让 AI 从一个简单的聊天机器人，变成了一个具备**自我纠偏能力**的专业编剧助手。”

## 你“封装”的专属 Skill 逻辑

**Skill 名称：Context-Aware-Commit-Agent**

> “我下载了 OpenCommit 作为基础，但发现它不理解我的业务逻辑（比如它不知道某个文件属于‘短剧角色配置’还是‘游戏数值调整’）。于是我**封装**了一个更上层的 Skill。”

**你的封装逻辑（干货）：**

1. **注入元数据（Metadata Injection）**： 在调用 git diff 之前，我的 Skill 会先读取当前项目的 README.md 或 project.godot。这样生成的 Commit 不会只说 update [script.gd](https://script.gd/)，而会说 feat(ui): 优化对话框弹出动画，匹配 Neva 风格美术资源。
2. **强制结构化输出（Structured Output）**： 我定义了严格的 JSON Schema。要求 AI 必须返回 type, scope, subject 三个字段。JSON{ "type": "feat", "scope": "character-system", "subject": "增加主角‘盏盏’的矿物颜料材质动态切换逻辑" }
3. **自动化流水线（Agentic Workflow）**： “我不只是生成文字，我把这个 Skill 挂载到了我的 **Vibe Coding** 工作流中。当我完成一段功能描述，Agent 自动改完代码后，会立刻触发这个 Skill。如果校验通过，它会自动执行 git commit。这就实现了从**自然语言指令**到**规范化代码提交**的闭环。”
