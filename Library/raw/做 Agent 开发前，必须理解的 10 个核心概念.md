# X 上的 Stanley：“做 Agent 开发前，必须理解的 10 个核心概念” / X

https://x.com/Stanleysobest/status/2058764854736121987?s=20

很多人第一次接触 AI Agent，会有几个直觉问题：

它为什么知道下一步该做什么？

它怎么决定要不要调用工具？

它怎么记住前面发生过的事？

它犯错之后能不能自己改？

其实，Agent 并不是“更聪明的聊天机器人”，而是一套由 **大语言模型、工具调用、任务规划、记忆系统、上下文管理、安全控制** 共同组成的智能执行系统。

## 一、Agent 核心循环：Perceive → Think → Act → Observe

Agent 最基础的运行方式，可以理解成一个循环：

```text
Perceive（感知）→ Think（思考）→ Act（行动）→ Observe（观察）
```

小白可以把它想象成一个人在做任务：

先看到问题，也就是 **Perceive**； 再分析应该怎么做，也就是 **Think**； 然后执行一个动作，比如搜索、读文件、调用接口，也就是 **Act**； 最后观察结果，再决定下一步，也就是 **Observe**。

这就是 Agent 和普通 ChatBot 最大的区别：普通 ChatBot 通常只“回答”，而 Agent 会“边做边看结果，再继续调整”。

开发 Agent 时，最容易出问题的是缺少 **Think** 这一步。如果模型没有先判断任务状态，就直接行动，很容易陷入重复调用工具、反复搜索、不断重试的死循环。

## 二、工具调用机制：Function Calling 与 MCP

Agent 能做事，靠的是 **工具调用（Tool Calling）**。

大语言模型本身不会真的打开浏览器、读数据库、发邮件、改代码。它真正能做的是：判断“我现在应该调用哪个工具”，然后生成一段结构化参数，让外部系统去执行。

这里有两个重要概念：

**Function Calling**：让模型用结构化方式表达“我要调用哪个函数、传什么参数”。 **MCP（Model Context Protocol）**：让模型所在的应用和外部工具、数据源建立标准连接。

你可以这样理解：

Function Calling 负责“模型怎么说”； MCP 负责“工具怎么接进来”。

比如用户说：“帮我查一下今天北京天气。”

模型不会自己查天气，而是生成类似这样的意图：

```text
{
"tool": "get_weather",
"arguments": {
"city": "北京"
}
}
```

真正访问天气接口的是宿主程序。

工具调用的关键不只是“有没有工具”，而是 **工具描述是否清楚**。如果工具名、参数、使用场景写得模糊，模型就会选错工具、传错参数，甚至在不该调用工具时乱调用。

## 三、规划与任务分解：Agent 怎么把大任务拆小

用户经常给 Agent 一个很大的任务，比如：

“帮我调研 3 家竞品，并输出一份对比报告。”

这个任务不能一步完成。Agent 需要先做 **Planning（规划）**，把大任务拆成多个子任务：

1. 明确要调研哪些竞品
2. 搜集每家公司的产品信息
3. 比较功能、价格、用户群体
4. 整理成表格
5. 生成最终报告

这就叫 **任务分解（Task Decomposition）**。

更专业一点说，Agent 要处理的是一个带依赖关系的任务图。比如“写报告”依赖“收集资料”，“做对比”依赖“拿到每家公司信息”。

执行策略通常有两种：

**顺序执行**：一步一步来，适合依赖关系强的任务。 **并行执行**：多个子任务同时跑，适合互不依赖的任务。

一个优秀 Agent，不是盲目执行，而是先判断任务结构，再决定执行顺序。

## 四、记忆系统：短期记忆、长期记忆、工作记忆

Agent 要像一个“持续工作的助手”，就必须有记忆。

常见记忆分三类：

**短期记忆（Short-term Memory）**：当前对话里刚刚发生的内容。 **长期记忆（Long-term Memory）**：跨会话保存的用户偏好、历史任务、项目背景。 **工作记忆（Working Memory）**：当前任务执行过程中临时保存的中间状态。

小白可以这样理解：

短期记忆像“刚聊过的话”； 长期记忆像“通讯录和个人档案”； 工作记忆像“做题时的草稿纸”。

比如你让 Agent 写代码，它需要记住：

当前项目结构是什么； 刚才改了哪个文件； 测试失败在哪里； 下一步应该修哪个问题。

这些都不是单次回答能解决的，而是需要记忆系统参与。

## 五、上下文窗口管理：Agent 的“内存管理”

大语言模型有一个限制，叫 **上下文窗口（Context Window）**。

它决定了模型一次最多能看到多少内容。内容太多时，模型不可能把所有文件、所有历史对话、所有工具结果都塞进去。

所以 Agent 必须做 **上下文管理（Context Management）**。

常见策略有四种：

**按需加载**：只把当前任务相关的信息放进上下文。 **摘要压缩**：把长内容总结成短摘要，减少 token 消耗。 **子 Agent 分担**：让不同 Agent 分别处理不同信息。 **去除冗余**：重复内容、无关日志、过期信息不要塞给模型。

这一步很关键。很多 Agent 失败，不是模型不够聪明，而是上下文太乱：该看的没看到，不该看的塞了一堆。

## 六、ReAct 范式：边思考边行动

ReAct 是 Agent 领域非常经典的范式，全称可以理解为：

**Reasoning + Acting**

也就是“推理”和“行动”交替进行。

它的基本结构是：

```text
Thought：我需要先查资料
Action：调用搜索工具
Observation：拿到搜索结果
Thought：结果不够完整，需要换关键词
Action：再次搜索
Observation：得到更准确的信息
```

ReAct 的价值在于：Agent 不只是一次性给答案，而是能根据工具返回结果继续调整。

这非常像人类工作：

先想一下； 做一步； 看结果； 再决定下一步。

不过，并不是所有任务都需要 ReAct。简单问答、固定流程、无需工具的任务，用 ReAct 反而会增加成本和延迟。

## 七、多 Agent 协作：复杂任务需要分工

当任务变复杂，一个 Agent 可能不够用。

这时就会出现 **Multi-Agent Collaboration（多 Agent 协作）**。

比如做一个软件项目，可以拆成：

产品 Agent：理解需求 架构 Agent：设计系统结构 编码 Agent：实现功能 测试 Agent：编写测试并发现问题 审查 Agent：检查代码质量和安全风险

多 Agent 协作有两种常见模式：

**中心化编排**：一个主 Agent 负责分配任务，其他 Agent 执行。 **去中心化协作**：多个 Agent 相互沟通，自行协商任务。

中心化更容易控制，适合工程落地；去中心化更灵活，但也更容易失控。

真实产品里，通常会优先选择中心化编排，因为可观测、可调试、可控性更强。

## 八、错误处理与自我纠正：Agent 犯错后怎么办

Agent 一定会犯错。

可能是工具调用失败，可能是参数写错，可能是理解错任务，也可能是模型产生幻觉。

所以 Agent 必须具备 **Error Handling（错误处理）** 和 **Self-Correction（自我纠正）** 能力。

常见错误信号有三类：

**工具返回错误**：比如 API 报错、文件不存在、权限不足。 **环境反馈错误**：比如测试失败、编译失败、网页加载失败。 **模型自检错误**：模型发现自己的计划不完整或前后矛盾。

应对策略可以从轻到重：

重试一次； 换参数再试； 换工具处理； 回到规划阶段重新拆任务； 请求用户确认。

好的 Agent 不会假装永远正确，而是能识别失败、解释失败、修正失败。

## 九、安全与对齐：给 Agent 装上刹车

Agent 能调用工具，也就意味着它可能造成真实影响。

比如删除文件、发送邮件、修改数据库、发起支付、执行脚本。

所以必须做 **安全控制（Safety Control）** 和 **对齐（Alignment）**。

一种常见做法是风险分级：

低风险操作：读取信息、搜索资料，可以自动执行。 中风险操作：修改草稿、生成文件，需要记录日志。 高风险操作：删除数据、发邮件、付款、发布内容，必须让用户确认。

这叫 **权限分级模型（Permission Model）**。

更稳妥的做法是 **Defense in Depth（纵深防御）**：

第一层：系统提示词约束 第二层：工具权限限制 第三层：操作前用户确认 第四层：日志、审计与回滚机制

Agent 越强，越需要刹车。否则它不是助手，而是风险源。

## 十、编排框架与实战选型：怎么真正造一个 Agent

当你真正开始开发 Agent，会遇到一个问题：

到底是直接调模型 API，还是用现成框架？

通常可以分三层：

**轻量封装**：直接调用 OpenAI、Claude、Gemini 等模型 API，自己写工具调用逻辑。适合简单项目。 **Agent 框架**：使用 LangChain、LlamaIndex、AutoGen、CrewAI 等框架，快速搭建 Tool、Memory、Planner。适合中等复杂度项目。 **自研编排系统**：自己设计任务调度、权限、记忆、日志、评测和多 Agent 协作。适合生产级复杂系统。

小白入门建议：

先从 Function Calling 开始； 再做一个带工具调用的小 Agent； 然后加入 Memory 和 Context 管理； 最后再考虑多 Agent 和复杂编排框架。

不要一上来就堆框架。Agent 开发最重要的不是“用了多少高级库”，而是你是否理解它的运行机制：

它如何感知任务； 如何规划步骤； 如何调用工具； 如何观察结果； 如何处理错误； 如何控制风险。

理解了这 10 个概念，才算真正摸到 Agent 开发的门。
