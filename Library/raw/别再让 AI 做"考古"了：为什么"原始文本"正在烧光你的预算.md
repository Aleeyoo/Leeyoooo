# 别再让 AI 做"考古"了：为什么"原始文本"正在烧光你的预算

https://www.wisme.ai/plaza/articles/bie-zai-rang-ai-zuo-kao-gu-liao-wei-shi-yao-yuan-shi-wen-ben-zheng-zai-shao-guang-ni-de-yu-suan-152a77ce

## 核心论点

Sutton 警告过不要手工编码智能。如今，企业却把这条教训当作"原始记忆即可"的通行证，而 **Token 账单正在爆炸** 。

> Sutton 说得对：手工编码的智能最终会输给那些善用计算能力的通用方法。但错误在于，把这当作"企业记忆可以保持原始文本"的许可。

## 当前行业的错误实践

企业正在犯这个错误：

- 给 Agent 连接更多工具
- 扩大上下文窗口
- 保留更长的历史记录
- 使用更混乱的检索管道

结果： **Token 预算开始失控** 。

## 知识图谱的局限

传统知识图谱通过建模实体和关系解决了部分问题，但许多图谱 **过早冻结了一种本体** 。它们把一个团队的解释变成了基础设施。

## 正确的边界

> **语义应在数据摄入时处理，本体应在检索时应用。** 持久化事实一次，之后再用业务视角解读。

这就是 **Company Brain 论点** ：

- 状态保存一次
- 视角后续应用
- 把算力花在判断上，而不是重新发现公司知识

![核心架构边界：摄入时处理语义，检索时应用本体](https://www.wisme.ai/media/canvas-doc-slots/bcf336d3-a9c0-4494-bbcf-8f275a42ade4/deef0b8f-5d62-4039-a5ca-42ffbc3ebd63-framework-semantics-ontology-boundary.jpg)

## 误解"苦涩教训"

读 Sutton 的《苦涩教训》可能会让你觉得组织信息是浪费时间。 **这不是 Sutton 的意思。**

Sutton 的观点是：善用计算（尤其是搜索和学习）的通用方法，最终会胜过试图将人类知识直接编码进 AI 系统的方法。他警告的是 **手工编码的智能** ，而不是 **保存状态** 。

## 行业正在内化一个更粗糙的教训

> **停止组织数据。**

于是我们：

- 把原始文本倒进向量数据库
- 扩大上下文窗口
- 把 Agent 接入每个内部系统
- 指望暴力计算在检索时搞定意义

RAG 让这种模式变得有用：把知识留在模型外，需要时检索，让模型合成答案。大上下文窗口让一次性放入更多工作材料变得更容易。这招经常奏效，所以很诱人。 **但它也让每个问题都变成了考古。**

## 问题已变成预算危机

随着 Agent 采用率上升，企业正在走向 **Token 最大化** ：

- 更大的上下文窗口
- 更多的工具调用
- 运行时间更长的 Agent
- 更多的重试
- 更多的日志
- 更多的检索
- 对不需要前沿智能的问题也使用前沿模型

Anthropic 的上下文窗口文档将其描述为"工作记忆"，并说明消息、工具使用和输出都计入有限的 Token 预算。结果是：

- 更高的支出
- 更奇怪的失败模式： **公司的混乱程度决定了 AI 预算**

## 计算能力的正确用法

计算在学习方面非常出色。但当你用它 **反复重新发现组织本应已知的状态** 时，就是浪费。

每次 Agent 或员工提问，系统都在消耗 Token 和延迟，重建本应已保存的关系。

> **错误在于把结构化状态和手工编码智能混为一谈。**

Company Brain 不会试图比模型更聪明。它 **阻止模型在每个问题上支付同样的考古税** 。结构不会对抗规模，而是聚焦规模。

## 结构的作用

当你在数据摄入时应用结构，你并没有拒绝"苦涩教训"。你是在 **给计算提供更好的运行环境** 。

- 搜索原始数据湖 → 昂贵的暴力问题
- 遍历有组织的语义状态 → 更窄、更便宜、更容易验证

## 核心边界

| 阶段 | 处理内容 |
| --- | --- |
| **摄入时** | 语义（Semantics） |
| **检索时** | 本体（Ontology） |

**语义状态** 是公司对"发生了什么"的记忆，在任何团队决定其含义之前。它记录持久的关系，而不强制将其塞入单一业务解释。它不会一劳永逸地决定一个事件主要是：

- 流失风险
- 合规暴露
- 路线图信号
- 还是工程依赖

这种区分是架构的核心。

## 三个思维实验

### 实验 1：语义冲突

给一个小型快速模型三条原始文本记录：

> "模型在定价变更后失败了。"
>
> "财务在定价变更后更新了模型。"
>
> "增长团队说模型不再匹配活动表现。"

问： **哪个模型失败了，谁应该调查？**

"模型"这个词承担了太多工作。它可能指：

- 生产中的 ML 模型
- 财务预测模型
- 活动归因模型

"定价变更"也有多重含义：

- 产品定价
- 预测假设
- 折扣逻辑
- 广告竞价
- 活动经济学

在真实公司中，这些句子来自不同地方：ML 事故频道、财务规划文档、增长分析线程。一旦被倒进原始文本， **来源上下文很容易被抹平** 。

前沿模型可能答对，但需要大量上下文。小型模型可能把含义坍缩成一个泛化的"模型"并编造一个负责人。 **无论哪种方式，你都在付钱让模型重建本应在检索前就保存好的区分。**

现在用语义状态摄入同样的记录：

```
[ML模型] -> (失败于) -> [定价变更] -> (所有者) -> [ML平台]
[财务模型] -> (更新于) -> [定价变更] -> (所有者) -> [财务]
[活动模型] -> (不匹配于) -> [活动表现] -> (所有者) -> [增长]
```

语义标签不是答案。它是 **让更便宜的模型无需把每个歧义词都当作推理问题就能到达答案的环境** 。

公司里充满了这样的词："模型"、"账户"、"管道"、"所有者"、"发布"、"承诺"、"阻塞点"、"风险"、"事故"。 **第一课：原始文本让歧义变得昂贵。**

### 实验 2：多跳所有权陷阱

构建一个更丰富的公司历史：

| 文档 | 内容 |
| --- | --- |
| 6 个月前 | Sarah 构建了计费模块 |
| 2 个月前 | Priya 在 Sarah 转到基础设施后成为计费负责人 |
| 昨天 | 计费仍依赖 Stripe API |
| 昨天 | Stripe API 密钥周二过期 |
| 今早 Slack | Sarah 说："联系 Priya，我只构建了第一版。" |

问： **周二谁应该修复 Stripe 问题，有什么证据支持？**

原始文本转储仍然迫使模型区分"构建者"和"当前负责人"。语义状态可以预先保存这种区分。

## 结论

> **计算是学习的天才，却是考古的废物。**

不要混淆"结构化状态"和"手工编码智能"。Company Brain 不会试图比模型聪明，它只是让模型不必在每个问题上都支付考古税。

**结构不会对抗规模，它聚焦规模。**
