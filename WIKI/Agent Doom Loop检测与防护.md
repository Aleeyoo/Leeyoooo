# Agent Doom Loop检测与防护

> [!abstract]- AI 摘要
> Doom Loop 是 Agent 持续执行但始终没有有效进展的隐蔽故障模式，不同于传统死循环，它的各项监控指标看似正常但任务进度为零。本文剖析了四种 Doom Loop 的形成机制、OpenClaw 的两道防线设计以及让长任务 Agent 真正可靠所需的五层外围基础设施。

## 扫读

> [!tip] 💡 一句话
> Doom Loop 是 Agent 在 ReAct 循环中原地打转的隐蔽故障——token 在烧、日志在滚、指标都正常，但任务毫无进展，破解之道是断路器加工具循环检测两道防线，以及模型外围的状态、规划、执行 trace、验证和硬停止五层基础设施。

> [!important] 📌 关键结论
> - Doom Loop 有四种典型形态：相同调用相同结果的确定性死循环、调用不存在工具的幻觉重试、轮询工具等待永不发生的事件、两个操作交替振荡的 Ping-Pong
> - 第一道防线——重试端断路器：上下文压缩最多 3 次，总重试硬限 32-160 次（根据候选模型数动态计算），所有错误路径共用同一计数器
> - 第二道防线——工具循环检测：哈希指纹 + 滑动窗口（30 条历史），两级告警（warning 提示自主纠正，critical 直接终止），覆盖四种检测器
> - 模型外围五层：状态（外部持久化）、规划（调度单而非 checklist）、执行 trace（工具输出落盘）、验证（机器验证 + 环境验证 + 独立评价三档）、硬停止（预算/安全边界写死）
> - 压缩并不能打破 Doom Loop——压缩后 Agent 会继续原工具调用再次卡死，需要压缩后开启观测窗口检测循环是否持续

> [!quote] 🎬 可行动项
> - 检查现有 Agent 工作流是否实现了工具调用指纹追踪：至少记录工具名 + 参数哈希，在滑动窗口内检测重复模式
> - 实现两级告警阈值：同一工具同一参数 ≥10 次给 warning（让 Agent 自主纠正），≥20 次直接终止
> - 建立外部状态存储（progress.md 或数据库），确保任务进度、决策记录不在 context 丢失
> - 制定硬停止规则：任务范围扩大、预算逼近上限、验证连续失败、操作涉及删除/生产数据——这些条件写死在系统中

## 精读

### 论证链

```
现象层：Agent 运行两小时任务进度为零 —— 没有卡死、没有报错、指标正常 —— 这是 Doom Loop，和传统死循环的本质区别在于每一轮 ReAct 循环都符合模型的训练模式，Agent 自身感知不到异常。

原因层：ReAct 循环本身没有问题，问题在于四类场景让循环失去信息增益：
1. 相同调用相同结果 → 确定性死循环，模型每一轮做相同决策
2. 幻觉工具名 → 返回"工具不存在"，Agent 解释为"暂时不可用"继续重试
3. 轮询卡死 → 等待永不发生的事件，Agent 不知道何时放弃
4. Ping-Pong → A→B→A→B 交替，每侧都"在工作"但整体无推进

四种场景的共同本质：工具一直在调用，但每一轮都没有产出新信息。

解决层：
- 第一道防线（断路器）：容错重试必须有上限，所有错误路径共享计数器
- 第二道防线（检测器）：哈希指纹 + 滑动窗口 + 两级告警，四种检测器覆盖四类场景
- 压缩后观测窗口：压缩成功不代表打破循环，需额外 3 次观测窗口验证

升维层：Doom Loop 只是"状态、规划、验证"三位一体失控中最容易被看见的一种 —— 长任务 Agent 的根因是带不住状态、估不准工作量、评不好自己的输出。解决之道是模型外五层基础设施。
```

### 关键引述

> "Doom Loop——Agent 持续执行，却始终没有有效进展的状态。跟普通的死循环不一样。死循环 CPU 跑满、进程僵住，监视器一眼就能看出来。Doom Loop 不会：它每一步都按 ReAct 的逻辑跑，工具在调用，模型在思考，token 在烧，日志一直在滚——指标都正常，只是这些动作合起来没在推进任务。"

> "带不住状态，估不准工作量，评不好自己的输出。这三件事一起出现，就是长任务最常见的失控链路——状态、计划、验证一起垮。"

> "Doom Loop 是架构问题，不是模型问题。断路器和循环检测能挡掉最坏的情况，但让长任务真正可靠，还得靠上面这五层一起在线。"

### 局限与盲区

- 本文未覆盖：不同类型 Agent（代码生成、数据分析、对话助手）的 Doom Loop 检测阈值应如何差异化设置，文中给出的 10 次/20 次阈值是 OpenClaw 的特化参数。Ping-Pong 振荡检测中的"结果无变化"如何判定——对于返回动态数据（如时间戳、实时价格）的工具调用，简单的哈希比较会失效
- 隐含假设：假设 Agent 使用的是 ReAct 循环架构，对于 Plan-and-Execute、Tree-of-Thought 等其他 Agent 架构，Doom Loop 的表现形式和检测方法可能完全不同。假设工具调用的"进展"可以通过输出哈希变化来衡量，但对于渐进式任务（如逐行写入文件），每一轮输出都不同但可能无实质进展
- 可能的反例：某些任务确实需要大量重复调用（如批量处理、分页抓取），简单的重复计数检测会产生误报。对于探索性任务（如开放式研究），"无进展"的定义本身就是模糊的，硬性断路器可能过早终止有意义的探索
- 文中提出的"五层基础设施"是方向性框架，缺少每一层的具体实现模式、数据格式和集成方式，从概念到工程落地还有较大距离
- 未讨论在受限环境（如无文件系统访问的沙箱、Serverless）中如何实现外部状态存储
