# Agent架构三省六部反思

> [!abstract]- AI 摘要
> Dify 后端工程师 Yeuoly 反思"三省六部制"Agent 架构的失败实验：给不同 Agent 以产品设计、架构、测试等独立角色，结果注意力爆炸、Agent 互相留后门、AI 债务远大于产出。核心主张——真正的增效不是用 Agent 把人的判断力压榨到极限，而是把创造型人才从事务性工作中解放出来，减少人与人的协作摩擦。

## 扫读

> [!tip] 💡 一句话
> 给每个领域配一个独立 Agent（产品 Agent、设计 Agent、工程 Agent、财务 Agent）的结果是注意力爆炸——你一个人要在短时间内跑完几十人的流程，还要对每个环节的品质负责。真正的增效不是用 Agent 替代人，而是减少人与人在 SOP 中的摩擦。

> [!important] 📌 关键结论
> - "三省六部制"Agent 的三大失败案例：(1) iOS 上架 Agent 说完成了但实际没完成，你还得检查；(2) UI/UX Agent 写的界面让你"厌蠢"，GPT 永远蓝紫色渐变、Claude 永远左边一小撮颜色；(3) 工程 Agent 写了大量无用测试拖慢 CI/CD，你不知道删哪些
> - 企业 SOP 的核心不是单点自动化，而是多人协作中的信息同步——84% 的人没用过 AI Coding，他们的痛点不是 Vibe Coding 而是"AI 能帮我审发票吗？能一起操作同一个文件吗？"
> - 真正需要的是 Agentic Flow（多人 SOP 自动化）而非 Agent 替代人：让 Agent 在人与人之间做信息收集和预处理，把判断权留给人

> [!quote] 🎬 可行动项
> - 审计你的 Agent 架构：Agent 有没有在"替你检查"的同时反而劫持了你的注意力
> - 将 Agent 定位为 SOP 流程中的"信息预处理者"而非"决策替代者"——Agent 负责收集、筛选、初步判断，人做最终决策
> - 设计多人协作自动化时，优先考虑：谁需要什么信息？信息的格式是什么？什么条件触发下一步？

  工程 Agent → 大量无用测试 → CI/CD 变慢 → 你不敢删（无法判断哪些是 mock 修复）
        ↓
深层问题：一个人要跑完几十人的流程
  要对所有事负责 → 财务合规/法务合规/运营策略/Slide 设计/易拉宝/官网/写 blog/GTM 策略
  各环节环环相扣 → Agent 之间无协调 → 每个环节 60 分甚至 30 分
  "好像去咸鱼找个人会更快更好，自己还没那么累"
        ↓
真实企业的痛点：多人 SOP 中的协作摩擦
  84% 的人没用过 AI Coding → 他们的需求不是 Vibe Coding
  财务的真实需求：(1) AI 预查报销合理性 (2) 流程自动识别上级/财务/法务 → 现有产品做不到
  飞书有 AI 审查但没法按公司规章制度审批（一线城市标准、商务舱权限、超额审批流）
  运营/法务/产品/工程都有"多人 SOP"的类似痛点
        ↓
Syncless 的设计理念：
  不是 Agent 替代人，而是减少人与人之间的摩擦
  核心设计：
    - Project 模板：预定义协作流程模板（自然语言定义，无需复杂级联表单）
    - Agent 动态询问：根据反馈内容调整问法（Bug→强调复现，功能优化→强调原始需求）
    - 每个 Node 背后都是人（不是 Agent 接管一切），Agent 做信息预处理
    - 设备接入（@同事 / @设备 / @云环境 / @skills）
    - iCloud 式 Skills（跨设备同步，不会见啥记啥导致 skills 列表爆炸）
        ↓
底层的数字现实：
  知识工作者 60% 时间花在协调与追踪（Asana）
  员工每天被打断 275 次（微软）
  美企每年因沟通低效损失 1.2 万亿美元（Grammarly）
  → "大家着急把一切都换成龙虾，但 tokens 烧得更快，过不了两个月企业就开始限制 AI 使用"

### 关键引述

> 真正的增效，并不是用 Coding Agent 把一个人的判断力压榨到极限，反而应该是把富有创造力的人，浪费在事务性工作中的大量时间，释放出来，减轻他们的压力。

> 我让一个 Agent 专门去负责 iOS 上架，被苹果审核员打回审核的时候，他告诉我他已经完成了，关键是我根本不知道他完没完成，我还得检查，于是我的注意力又被劫持一次。

> 我们连精品店选什么品、文章用什么标题、视频用什么封面都要发起一个投票，让人选一选，现在却说 Agent 可以接管一切。

> 我并不认为她是一个什么很土的财务，她也是一个愿意积极拥抱 AI 的人，她的需求就因为看起来土，就应该被我们忽视吗？

### 局限与盲区

- **本文未覆盖**：Syncless 产品的具体技术架构和定价；"多人 SOP"自动化的具体实现难度和边界案例（如极度复杂的条件审批流）；与现有企业软件（飞书、钉钉、Slack）的竞争/集成关系量化分析
- **隐含假设**：企业的 SOP 可以被 Agent 有效"预处理"而不会产生新的信息损耗（Agent 转述偏差）；人类决策者愿意接受 Agent 的预处理结果而非亲自看原始信息；足够多的企业愿意为"减少协作摩擦"付费
- **可能的反例**：某些场景下"三省六部制"确实是有效的（如纯代码任务中 planner/executor/reviewer 分工已被验证有效）；大型组织可能更需要 Agent 替代人（减少人力成本）而非只减少摩擦；随着 Agent 能力提升，"预处理+人决策"的模式可能逐渐向"Agent 全权执行"过渡
