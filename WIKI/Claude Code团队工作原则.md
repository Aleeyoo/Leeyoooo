# Claude Code团队工作原则

> [!abstract]- AI 摘要
> Claude Code 工程总监 Fiona Fung 分享 AI 原生团队的运作原则：当代码不再是瓶颈，所有围绕"写代码很贵"设计的流程（规划、评审、角色分工、知识共享）全部需要重建。核心原则：JIT 规划、每遇重复即自动化、Trust but Verify 评审、品味优先于手速、主动删除过时流程。

---

## 扫读

> [!tip] 💡 一句话
> 代码生成不再瓶颈后，瓶颈"转移"到了验证、评审、安全——Claude Code 团队的应对是：JIT 规划替代长篇设计文档、每遇重复即追问"能不能自动化"、Trust but Verify 的评审模式、招人看品味不看手速、管理者主动删除过时流程。

> [!important] 📌 关键结论
> - 瓶颈转移是核心诊断：旧瓶颈（写代码/发布产能）→ 新瓶颈（验证/评审/跨职能协作/安全），就像从马车到汽车不只是换发动机，整个交通系统都要重建
> - 五个旧流程正在失效：(1) 规划方式——六个月路线图三个月就过时；(2) 代码所有权——谁写的变成了奇怪的问题；(3) 代码评审——新规模新形态新工具；(4) 团队构成——角色边界在模糊；(5) 知识共享——文档不再是唯一真相来源
> - 五个新规范：(1) JIT 规划——在对的时间做恰好足够的规划，原型先行，代码赢才算数；(2) 自动化成为肌肉记忆——每遇重复工作条件反射式追问"能否自动化"；(3) Trust but Verify——Claude 接 60-70% 的 review 工作量（风格/lint/bug），人聚焦在法律合规/信任边界/品味判断；(4) 招人看两种特质：有产品 sense 的创意 builder + 深厚系统背景的工程师；(5) 扁平组织+主动删流程
> - "Building is cheap, arguing is expensive"——两人方案有分歧，十分钟做两个原型看实物，而非各写 PPT 开两轮会

> [!quote] 🎬 可行动项
> - 在下次遇到团队争论时，尝试"原型决胜负"：让 AI 把双方方案各做一个原型，实物对比替代 PPT 争论
> - 培养团队的自动化肌肉记忆：每周找一个重复性工作，花十分钟用 AI 自动化掉——从高频小事开始（客户反馈汇总、代码同步、环境检查）
> - 审视当前 Code Review 流程：哪些部分可以自动化（风格/lint/补测试/bug 捕获），哪些必须保留人审（安全/合规/品味/架构方向）
> - 一个月检查一次团队流程清单：有没有可以删除的会议、步骤、审批？主动站出来说"这个不需要了"

## 精读

### 论证链

```
历史前提：软件工程所有流程（瀑布/敏捷/评审/文档）本质围绕"写代码太贵"设计
  工程师时间是最贵资源 → 大量规划、需求文档、评审、会议来管理这个资源
        ↓
核心诊断：瓶颈转移 → 写代码不再是瓶颈
  旧瓶颈（灰色）：写代码产能、发布产能
  新瓶颈（黑色）：验证、评审、跨职能协作、安全
  → 围绕旧瓶颈设计的全部流程必须重新评估
        ↓
五个正在失效的旧流程：
  ① 规划：六个月路线图三个月过时 → JIT 规划，原型先行，写完再补文档
  ② 代码所有权：谁写的变成奇怪问题 → Agent 产出的大量代码归谁
  ③ 代码评审：规模和形态完全不同了
  ④ 团队构成：PM 写代码、工程师做设计、角色边界消融
  ⑤ 知识共享：文档不再是唯一真相来源
        ↓
五个新规范：
  ① JIT 规划：砍掉写代码前的设计文档（对大部分工作是 theater）
     + 加码验证——AI 原生工作流中 bug 出现方式不同
     + "Building is cheap, arguing is expensive"——原型决胜负
  ② 自动化肌肉记忆：每遇重复问题条件反射追问"能不能自动化"
     AI 时代自动化成本几乎为零 → 几乎所有重复超 3 次的事情都该自动化
     从小开始：今天一个、明天一个，一个月后工作方式完全不同
  ③ Trust but Verify 评审：Claude 接 60-70% review（风格/lint/bug/测试）
     人保留：法律合规、信任边界/安全敏感代码、产品方向和品味判断
     信任与验证的边界是动态的，必须不断重新评估
  ④ 角色变化：PM 写代码、工程师做内容、角色边界模糊
     招人看两种特质：有产品 sense 的创意 builder（Taste is scarce, typing is not）
     + 深厚系统背景的工程师（subtly wrong is still wrong）
  ⑤ 团队推动：扁平组织 + 管理者从一线做起 + 主动删除过时流程
     人不会主动删流程，只会在旧流程上叠新流程 → 需要有人站出来
        ↓
三个未解问题（即使 Claude Code 团队也没有答案）：
  ① 还需要单独的 iOS/Android 团队吗？
  ② 全自动化 review 能推到多远？够快和漏掉重要东西的线在哪？
  ③ 角色越来越模糊时，如何确保所有角色对产出有信心？
```

### 关键引述

> "瓶颈没有消失，只是转移了。转移到了验证、代码评审、安全。"

> "Building is cheap. Arguing is expensive."

> "Taste is scarce, typing is not."

> "如果一件事你需要重复3遍以上，请想尽一切办法用AI将其自动掉。"

> "人不会主动去删除流程，只会在旧流程上面继续叠新流程，所以你得主动站出来，指名道姓地说出哪些流程可以走了。"

> "Pick your noisiest workflow. Ask if it still earns its place."

### 局限与盲区

- 本文未覆盖：小团队（<10人）vs 大公司（>500人）的实践差异——Claude Code 是中型团队的经验，在超大型组织中是否适用；如何在招聘中具体评估"品味"和"判断力"——这两个标准高度主观且难以量化；跨时区远程团队的自动化协作挑战
- 隐含假设：假设团队成员愿意且能够接受角色模糊化和技能跨界——实际上很多人习惯了明确的角色边界和分工；假设 Agent 产出的代码适合"Trust but Verify"——对于关键基础设施代码，这个信任边界可能不够
- 可能的反例：JIT 规划在合规要求严格的行业（金融、医疗）可能不够——监管要求的前置审批和文档不可跳过；扁平组织在超大规模团队中可能导致协调成本激增；自动化推送太激进可能产生"自动化债"——大量无人理解的自动化脚本堆积
