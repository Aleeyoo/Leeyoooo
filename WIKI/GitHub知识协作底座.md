# GitHub知识协作底座

> [!abstract]- AI 摘要
> 论证为何在 AI Agent 时代选择 GitHub 作为公司知识协作的基础设施：Git 是 AI 模型天然熟悉的协作语言、本地仓库能让 Agent 获得完整上下文、知识是"开放贡献受控合并"的共同资产。

---

## 扫读

> [!tip] 💡 一句话
> GitHub 不是更好的文档编辑器，而是更适合作为 AI Agent 操作的知识基础设施。AI 需要的不是功能丰富的文档系统，而是可本地同步、标准化、结构清晰、能被完整理解的原始信息层。

> [!important] 📌 关键结论
> - AI 模型天然熟悉 GitHub 的协作范式（已在大量开源项目的训练数据中学习过），不需要额外编写"怎么使用"的手册。Git 命令行、文件树、diff、blame 的语义几十年没变，对 Agent 是基础设施级的稳定接口。
> - 本地仓库能让 AI Agent 获得完整上下文，而不是通过搜索接口、API 分页一段段获取。多个 Agent 可以同时使用同一份本地知识，互不冲突。
> - 文档和代码的边界在 AI Agent 时代会变模糊。GitHub 可以同时容纳文档、代码、Prompt、Demo 和工具，是适合"同一个任务的不同表达放在一起"的环境。

> [!quote] 🎬 可行动项
> - 将公司长期价值的知识（工作日志、项目复盘、技术方案、决策记录）从飞书/Confluence 逐步迁移到 GitHub 仓库
> - 按敏感度分仓库管理：公开知识、部门知识、项目知识、高敏知识各入不同仓库
> - 让 Agent 通过本地 clone 的方式获取完整知识，而不是每次通过 MCP/API 查询

### 关键引述

> "选择和偏爱 GitHub，并不是因为它是一个更好的文档编辑器，而是因为它更适合作为 AI Agent 操作的知识基础设施。"

> "过去 Git 的门槛在于，人要亲自理解 branch、commit、PR、review、merge。现在那些难理解的概念，可以交给 AI 去理解；那些难坚持的规则，可以交给 AI 去遵守。"

> "Talk is cheap, show me the code. 这里的'code'不一定只是程序代码，也可以是文档、配置、Prompt、脚本、Demo，或者任何能被 Agent 理解和执行的原始信息。"

### 局限与盲区

- 本文未覆盖：从飞书/Confluence 迁移到 GitHub 的具体技术方案（格式转换、历史记录迁移、权限映射），非技术同事的实际使用体验和培训成本。
- 隐含假设：团队有一定的 Git/GitHub 基础或愿意让 AI Agent 代为操作。假设组织文化支持"开放贡献"的理念，对知识公开透明有共识。
- 可能的反例：对于强监管行业（金融、医疗），知识本地化带来安全风险可能超过效率收益；对于不需要 AI Agent 深度参与知识管理的小团队，迁移成本可能不值得。
