# Harness四层控制体系

> [!abstract]- AI 摘要
> IBM 工程师 Tejas Kumar 通过一个 Hacker News upvote 案例，层层叠加 Harness 将一个连登录都过不去的裸 Agent 变成稳定跑通完整流程的系统——四层 Harness（迭代上限、上下文压缩、验证步骤、登录接管）不改模型不改 Prompt，只改外面的执行框架。核心洞察：真正决定 Agent 稳定性的不是模型多强，而是 Harness 多厚。

## 扫读

> [!tip] 💡 一句话
> Harness 就是用确定性的工程系统去约束和支撑一个非确定性的模型——不改模型不改 Prompt，只加四层控制（迭代上限防失控、上下文压缩保跑完、验证步骤确认做成、登录接管区分什么不该让模型做），就把一个撒谎说"搞定了"的 Agent 变成了能稳定跑通完整流程的系统。

> [!important] 📌 关键结论
> - 裸模型 Agent 的典型失败模式：任务未完成却向用户汇报成功（Hacker News upvote 根本没点却说点了）——换更强模型或改 Prompt 都未必管用，因为问题不在模型能力而在缺失 Harness
> - Harness 五大组件：(1) 工具注册表——决定模型能调用哪些工具；(2) 上下文管理——控制哪些信息保留哪些丢弃；(3) 护栏——设定运行边界（最大轮数/工具调用次数/异常中断）；(4) Agent Loop——让模型一轮轮观察-思考-调用工具-接收结果；(5) 验证步骤——任务结束后核对结果是否真的完成
> - 四层 Harness 逐级叠加：(1) 迭代上限——超轮数中断防止死循环；(2) 上下文压缩——定期压缩历史只保留决策相关信息；(3) 验证步骤——把判断权从模型声称转移到对执行记录的核查；(4) 登录接管——识别模型不擅长的场景，用确定性代码接管后恢复控制权
> - 登录接管的核心认知：不是所有事都该让模型做——模型适合开放问题（理解、判断、泛化），但登录这种确定性流程应该用代码搞定，做完后把世界恢复到模型能继续发挥的状态

> [!quote] 🎬 可行动项
> - 审计现有 Agent 的 Harness 覆盖：检查这五层（工具注册表/上下文管理/护栏/Agent Loop/验证步骤）是否缺失，从缺失最严重的那层开始补
> - 为每个 Agent 添加至少两层最小 Harness：迭代上限（防止死循环烧 token）+ 验证步骤（任务结束后核对实际状态而非轻信模型声称）
> - 识别 Agent 工作流中"不该让模型做"的环节：登录、固定流程表单填写、确定性计算——用代码接管，完成后恢复控制权
> - 建立验证的证据链：验证不是再问一次模型"你做完了吗"，而是检查工具调用历史、URL 访问记录、DOM 状态变化等客观证据

## 精读

### 论证链

```
核心命题（一句话）：模型只是大脑，真正让 AI 进入真实世界工作的是 Harness
        ↓
案例演示：让一个裸 Agent 去 Hacker News 给帖子 upvote
  裸模型结果：碰到登录页就不知道怎么办 → 稀里糊涂告诉用户任务搞定 → 实际上根本没点
  诊断：问题不在模型能力，在缺失 Harness——换更强模型或改 Prompt 都不治本
        ↓
Harness 定义：包裹在模型外面的完整基础设施
  五大组件：工具注册表 + 上下文管理 + 护栏 + Agent Loop + 验证步骤
  核心功能：在非确定性模型外面加一层确定性控制系统
  为什么需要：模型不像程序那样给定输入就沿固定路径执行——可能跑偏、忘记目标、误判状态、撒谎
        ↓
四层 Harness 逐级叠加（不改模型、不改 Prompt）：
  L1 迭代上限：
    问题：无约束 Agent 容易陷入死循环（反复点同一个按钮）
    方案：执行轮数超阈值直接中断标记失败 → 至少保证失败任务在可控成本内结束
  L2 上下文压缩：
    问题：浏览器 HTML + 多轮工具调用日志迅速塞满上下文窗口 → Agent 被历史信息淹没
    方案：定期压缩历史上下文，只保留对下一步决策有价值的信息
    效果：加完两层后 Agent 开始变得可控
  L3 验证步骤：
    问题：Agent 说完成了系统就默认完成 → 模型声称完成 = 幻觉 ≠ 实际完成
    方案：任务结束后 Harness 额外跑一轮验证——检查工具调用历史中访问了哪些 URL、点了哪些按钮、DOM 状态是否变化
    关键：把判断权从模型单一输出转移到对真实执行记录的核查
  L4 登录接管：
    问题：Agent 不知道如何登录（填用户名密码）
    方案：每轮检查浏览器 URL → 发现进入登录态 → 触发确定性登录脚本（环境变量拿凭证→填表单→提交）
    → 登录成功的世界恢复到 Agent 能继续发挥的状态，Agent 完全不知道发生过什么
    核心认知：识别模型不擅长的场景，用代码接管，做完后恢复
        ↓
四层合起来的本质：用确定性工程系统约束和支撑非确定性模型
  L1 防失控 → L2 保跑完 → L3 验做成 → L4 识别什么不该让模型做
  从头到尾没换模型没改 Prompt，只改了外面的执行框架
  → 很多 Agent 的问题不是模型能力问题，是 Harness 工程问题
  → Harness 不是玄学，是可拆解、可测试、可优化的软件工程问题
```

### 关键引述

> "模型本身只负责推理，但真实世界是一个由状态、权限、页面、网络和异常流程组成的系统。只有推理能力，是无法稳定进入真实工作流的。"

> "从头到尾，Agent 的模型没换，Prompt 没改，改的全是它外面的执行框架。但 Agent 的表现，已经从一个连登录都过不去的系统，变成了一个能稳定跑通完整流程的 Agent。"

> "很多时候，真正决定 Agent 稳定性的，其实是 Harness。"

> "Harness 不是玄学。它是一整套可以被拆解、被测试、被优化的软件工程问题。"

### 局限与盲区

- 本文未覆盖：四层 Harness 之外的更多层级（如错误恢复策略、并发控制、审计日志、安全沙箱）——实际生产环境可能需要六到八层；每层 Harness 的实现细节和代码示例——演讲是概念演示而非完整教程；Harness 本身引入的故障模式——确定性的登录脚本也可能出错（密码过期、登录页改版），错误的接管可能导致比裸模型更隐蔽的失败
- 隐含假设：假设叠加 Harness 不会显著增加延迟——实际上每层验证和检查都会增加总体执行时间；假设"模型不擅长的事情"能被预先识别且覆盖——实际上很多边缘情况难以穷举；假设 Harness 的代码本身不会成为新的维护负担
- 可能的反例：极简单的任务（单次 API 调用）不需要四层 Harness，过度工程化可能得不偿失；某些复杂推理任务（如"判断这个 PR 是否应该合并"）的验证本身就依赖模型判断，无法用确定性代码替代；模型能力的持续提升可能让某些 Harness 层（如登录接管）在未来变得不必要
