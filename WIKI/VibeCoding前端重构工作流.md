# VibeCoding前端重构工作流

> [!abstract]- AI 摘要
> 利用 GPT（架构/文档）与 Opus（前端/交互）的异构分工模式，通过 Spec 驱动的渐进式重构和 AI 辅助 UI 设计迭代，完成移动端大规模 UI 重构。

## 扫读

> [!tip] 💡 一句话
> 用 GPT 管架构规划、Opus 管前端实现，通过详尽的 Spec 文档分阶段驱动重构，让非设计师也能通过 AI 迭代出可用的 UI。

> [!important] 📌 关键结论
> - GPT 与 Opus 的能力差异是"能用 vs 不能用"级别：GPT 擅长架构梳理和后端逻辑，Opus 擅长前端实现和交互细节。
> - 重构的核心时间应花在 Spec 文档上：先让 AI 梳理耦合点（40 个文件），生成近千行计划，再拆分为 4-5 个阶段逐阶段执行和讨论。
> - 非设计师设计 UI 的可行路径：用 iPad 画草稿 → Codex 生成渲染图 → 不断调整 prompt "抽卡"迭代 → 得到满意的视觉方向。
> - 与 AI 描述交互时，使用组件库术语（如 Accordion、Sheet、Dropdown）替代自然语言描述，既节省 token 又让 AI 理解更准确。
> - Storybook 是防止 AI 后续改坏组件的关键工具：在 AGENTS.md 中规定新增组件必须枚举所有状态（正常/空/加载/错误/禁用）。

> [!quote] 🎬 可行动项
> - 在开始大任务前先了解当前模型版本的擅长领域边界，据此分配不同性质的任务。
> - 重构前先让 AI 整理现有代码的耦合关系，生成完整 Spec 文档并分阶段拆分。
> - 非设计师可先用纸笔/iPad 画草稿，再用 AI 生成多轮渲染图迭代设计方向。
> - 熟悉 shadcn ui 等组件库的组件术语，作为与 AI 沟通交互需求的词汇表。
> - 在项目 AGENTS.md 中规定新组件必须创建 Storybook，枚举所有状态用于走查。

## 精读

### 论证链

```
1. **问题定义** → Lody 多端 UI 用 `isMobile()` 简单适配，交互别扭、字体和按钮过小，移动端需要专门重设计。
2. **模型能力认知** → 通过实际使用发现 GPT 和 Opus 的能力边界清晰不同，异构 Multi-Agent 是提升生产力的关键——不是 80 分和 90 分的差别，而是能用和不能用的差别。
3. **Spec 驱动重构** → 让 Codex 搜索 40 个耦合文件，整理成近千行计划文档，拆分为 5 个阶段（确认边界 → 拆纯移动端组件 → 重构核心 feature 移动端布局 → 设计新 UI → 测试发布），逐阶段 comment 讨论后执行。
4. **非设计师 UI 设计方法** → 先以用户视角考虑信息架构（入口看到什么、热路径、功能层级），iPad 画草稿 → Codex 生成真实渲染图 → 不断调整 prompt 迭代直到满意。
5. **组件术语沟通** → 用 shadcn ui 组件库的术语（Accordion, Sheet, Dropdown）替代自然语言描述，节省 token 且提高 AI 理解精度。
6. **Opus 前端实现** → 从上到下描述渲染图上的所有组件及其交互效果，第一遍复现大概，后续逐细节打磨。Web 技术栈的 HMR 热更新是快速迭代的关键优势。
7. **Storybook 防护层** → 新组件必须创建 Storybook 枚举所有状态，防止 AI 后续改动破坏已有样式和交互，同时覆盖空态和异常态。
```

### 关键引述

> 这些差异是使用了几次就能够明显感受得到的，因为不是 80 和 90 的差别，而是能用和不能用的差别。所以在做大的任务之前，先了解这些模型，每一次模型更新都需要重新去试探这种边界，这可以更好地事半功倍地完成任务。

> 非专业的朋友学习 vibe coding 就可以在日常工作的时候浏览网站的时候看到这种专业名词就记下来，不但节省 tokens 而且 AI 理解得更加清楚。
