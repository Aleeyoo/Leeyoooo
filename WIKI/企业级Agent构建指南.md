# 企业级Agent构建指南

> [!abstract]- AI 摘要
> 以一套报价 12 万的 Deep Research 系统为案例，从零拆解企业级 Agent 的构建逻辑——从"什么时候该用 Agent 而非 Workflow"的决策框架，到多 Agent 的编排模式、上下文管理、信息传递协议和评估体系。核心洞察：看懂了 Deep Research，你就看懂了企业级 Agent。

## 扫读

> [!tip] 💡 一句话
> Agent 和 Workflow 的核心区别：Workflow 是你告诉 AI 怎么做（预定义代码路径），Agent 是 AI 自己决定怎么做（ReAct 循环）。判断标准——这个任务能不能提前写成稳定流程？能，就先用 Workflow。不能，再考虑 Agent。

> [!important] 📌 关键结论
> - 多 Agent 的必要性来自两个瓶颈：(1) 单 Agent 的上下文窗口会"腐烂"（Transformer 的 n² 注意力复杂度导致上下文越长准确率越低）；(2) 单 Agent 只能串行工作。多 Agent 把任务分散到独立上下文窗口，既扩大了可处理信息量，又实现了并行
> - Agent 架构的核心设计原则：(1) 子 Agent 只返回总结不返回原始内容（上下文压力控制）；(2) 子 Agent 之间完全上下文隔离；(3) 信息传递核心原则是"传递结论不传递过程"
> - 评估多 Agent 系统必须看三层：小样本快速测试（20 个典型问题每次改完跑一遍）、LLM 评估（事实准确性/引用准确性/完整性/来源质量）、人工评估（自动化发现不了的"内容农场"问题）

> [!quote] 🎬 可行动项
> - 搭建 Agent 前先问："这个任务能不能提前写成稳定流程？"→ 能=用 Workflow，不能=用 Agent
> - 设计 Agent-Computer Interface（ACI）时：让模型"容易写"而不是让代码"优雅"——让模型在 Markdown 代码块写代码而非 JSON 里转义
> - 多 Agent 系统必须保留完整的追踪日志（tracing）：记录每个 Agent 的决策、工具调用、返回结果，出错时能回溯整个过程

## 精读

### 论证链

![[enterprise-agent-deep-research.jpg]]

```
Agent 的定义升级：
  不是"更聪明的 AI"，是"会自己动手的 AI"
  三能力组合：调用工具 + 自己规划 + 从反馈中调整
        ↓
何时用 Agent 的决策框架：
  简单任务 → 优化单次 LLM 调用（文本分类/总结/简单问答）
  中等任务 → Workflow（预定义代码路径，可预测易调试）
  复杂任务 → Agent（开放式问题，无法硬编码固定路径）
  判断标准：信息入口复杂 OR 执行路径不确定 → Agent
        ↓
Agent 工作方式：ReAct 循环
  "思考 → 行动 → 观察结果 → 再思考" 直到完成
  不是一次性给答案，而是根据反馈调整策略
        ↓
为什么需要多 Agent（两大瓶颈）：
  ① 上下文腐烂：Transformer n² 注意力 → 上下文越长准确率越低
     单 Agent 搜 200 个网页 = 60 万中文字 → 记不住
  ② 效率：单 Agent 串行 vs 多 Agent 并行（3 个子任务同时做）
  核心价值：不是只为了快，而是扩展"可处理的信息量"
        ↓
两种协作模式：
  编排模式（指挥+乐手）：主 Agent 规划→分配→子 Agent 执行→主 Agent 整合
    → 稳定、易控制，大部分系统用的就是这个
  自主模式（创业团队）：无固定老板，Agent 之间协商
    → 灵活但复杂、难调试
        ↓
信息传递协议（最关键的设计）：
  差：直接传递（子 Agent 把 3 万字原始内容全传给主 Agent）
  好：总结传递（压缩成 3000 字关键发现，附带主题+结论+来源）
  最优：结构化传递（统一格式：{主题, 关键发现[], 来源[]}）
  核心原则：传递结论，不传递过程
        ↓
上下文管理三策略：
  ① 分散上下文：每个子 Agent 独立窗口
  ② 压缩上下文：AI 总结对话历史保留任务目标+关键发现+下一步
  ③ 外部记忆：存到文件/数据库，需要时再读
        ↓
Deep Research 实战架构（6 步）：
  1) 用户输入 → 主 Agent 澄清需求 → 生成研究计划
  2) 主 Agent 拆解为多个子任务
  3) 创建子 Agent（每个拿到：原始问题+子任务+工具）
  4) 子 Agent 并行工作（搜索→总结→搜索→总结，交错思考 interleaved thinking）
  5) 主 Agent 整合所有子 Agent 的总结
  6) 引用 Agent 检查结论 → 添加来源引用
  总耗时：5-10 分钟
        ↓
评估与迭代三方向：
  ① 优化提示词（简单问题不要拆太多/直接比较拆 2-4 个子任务/工具选择写清楚）
  ② 优化工具 ACI（让模型容易写→Markdown 代码块而非 JSON 转义→降低错误率）
  ③ 优化协调（异步处理→哪个先完成先处理→不被最慢的拖住）
```

### 关键引述

> Agent 的核心能力不是回答问题，是解决问题。

> Workflow 是你告诉 AI 怎么做，Agent 是 AI 自己决定怎么做。

> 信息传递的核心原则：传递结论，不传递过程。

> 单 Agent 的上下文窗口再大，也要把所有材料塞进一个脑子里。多 Agent 可以把任务分散到独立的上下文窗口里，每个 Agent 只处理自己那一部分材料。

> 多 Agent 不是免费的。当任务本身足够复杂、结果价值足够高时，才值得用多 Agent 换取更大的信息覆盖和更高的完成率。

### 局限与盲区

- **本文未覆盖**：企业级 Agent 的具体定价模型和 ROI 计算方法；不同行业（客服、投研、编程、法律）的 Agent 架构差异；多 Agent 系统在安全合规（数据隐私、审计要求）方面的设计考量；Agent 系统的运维和监控方案细节
- **隐含假设**：企业客户有足够清晰的 SOP 来支撑 Agent 设计；LLM 的能力和价格会持续向有利于多 Agent 架构的方向发展；上下文压缩不会引入关键信息丢失
- **可能的反例**：某些企业级任务（如法律合规审查）不允许"总结传递"带来的信息压缩风险，必须保留全量上下文；编排模式中主 Agent 的规划错误会导致全局失败（单点故障）；随着模型上下文窗口持续增大（百万 token），多 Agent 的隔离优势可能被削弱
