# 企业统一智能脑架构

> [!abstract]- AI 摘要
> Single Grain 团队将散落在 Gong、Slack、HubSpot 和员工头脑中的公司知识重建为五层智能系统（Capture-Retrieval-Source Truth-Permissions-Feedback），核心洞察是：公司大脑的价值不在于存储更多信息，而在于知道检索什么、信任什么、谁可以看、如何将每一次纠错转化为更好的行为。持久记忆从"资产"变成"瓶颈"是这个系统的起点——当记忆文件吃掉 40% 上下文窗口时，真正的解法不是更多记忆，而是更聪明的检索。

## 扫读

> [!tip] 💡 一句话
> 公司大脑的真正优势不在记忆容量，而在信息与其使用之间的智能层——知道该检索什么、该信任哪个来源、该保护什么不该用、该怎样把每次人工纠错变成更聪明的行为。

> [!important] 📌 关键结论
> - 持久记忆本身会变成瓶颈：Single Grain 的持久记忆文件一度吃掉 40% 上下文窗口——Agent 有了更多信息，但不一定在正确时间拿到了正确信息，"技术上的更聪明"变成了"操作上的更混乱"
> - 五层架构的递进逻辑：Capture 提供原料 → Retrieval 决定在正确时刻交付正确上下文 → Source Truth 解决"哪个来源说了算"的信任问题 → Permissions 防止每个 Agent 看到不该看的内容 → Feedback 让每次人工纠错变成系统学习
> - Retrieval 是系统从"存储单元"变成"智能层"的分水岭：Agent 不需要公司全部历史，只需要与当前任务相关的 6 条关键上下文——写外发邮件和审查管道的上下文集合完全不同
> - Feedback Loop 是系统复利增长的引擎："每当你纠正 Agent 一次，那条纠正就应该变成未来的行为"——从人工修正到自动规则更新的管道是公司从"使用 AI"切换到"AI 随公司成长"的关键
> - 实际数据验证：2,862 个 Gong 通话记录转化为可操作的作战手册；15 通电话日处理产出 390 条洞察、470 个事实、125 个框架——一次通话不再是通话，而是一座可复用洞察的小矿

> [!quote] 🎬 可行动项
> - 跑一次 6 问审计：选一个当前浪费时间的重复性工作流（周报/管道审查/销售跟进/客户入职），回答——依赖哪些来源？来源冲突时谁说了算？每次需要什么上下文？永远不该看什么？哪些人工纠错重复发生？一次纠错如何变成未来规则？
> - 检查你当前的 Agent 记忆方案：持久记忆是否已经吃掉 >30% 上下文窗口？如果是，转向"记忆为原料、检索为操作系统"的思路，而不是继续堆记忆
> - 建立 Source Truth 层级表：将你的数据来源分类为"实时真相""历史语境""可参考不可引用""内部专用""禁止用于外部输出"等层级
> - 为每个 Agent 工作流设定权限边界——Agent A 能看什么、不能看什么，不要等泄漏发生后才补墙
> - 设计一条"人工纠正→自动规则"的最小闭环：某次人工修正触发了什么规则的创建或更新？这个管线是系统能否复利增长的关键

## 精读

### 论证链

```
起点：公司知识天然分散在 Slack、Gong、HubSpot 和"今天请假了的那个人"身上
  → 真正的优势不在收集这些知识的巨型文件夹（每家公司都已有），
    而在这些上下文与其应该驱动的工作之间的智能层
        ↓
第一阶段（失败）：无差别记忆策略
  做法：给每个 Agent 更多上下文 → 保存有用笔记 → 保留通话记录 → 让系统记住人类遗忘的
  结果（三周后崩溃）：持久记忆文件吃掉约 40% 上下文窗口
    → Agent 有了更多信息，但不是在正确时间拉取正确信息
    → "技术上的更聪明，操作上的更混乱"
  根因：人类变成了路由器——每个 Agent 输出依赖某人是否记对了通话、复制了正确的笔记、
        粘贴了正确的上下文、第五次纠正了同一个错误
        ↓
重构：记忆是原料，检索是操作系统
  旧流程：通话记录 → 随机笔记 → 人类记忆 → Agent 冷启动 → 人类重新解释
  新流程：Calls/CRM/SOPs/Slack → Retrieval（检索层）→ Agent → Work
            ↑                                  │
            └── 人工纠正 → 规则更新 ←──────────┘
        ↓
五层架构详解：
  Layer 1 - Capture（捕获层）：
    来源：通话、CRM 活动、内容决策、内部 SOP、Agent 输出、每日日志、人工纠正
    核心洞察：多数团队在这一层就停下了 → 把录音、文档存进向量数据库就叫它"脑"
    但那只是"存储单元"——不决策、不排优先级、不知道事实已过时、不知道两个文档冲突时谁该赢
  Layer 2 - Retrieval（检索层）：
    系统从"存储"升级为"有用"的分水岭
    核心问题：Agent 不需要公司全部历史，只需要与当前任务相关的关键上下文
    实例对比：
      写外发邮件 → 需要 ICP、offer、异议处理、历史活动表现、品牌声音、当前活动目标
      审查管道 → 需要交易阶段变化、停滞账户、最近通话笔记、异议、下一步、CRM 当前状态
      写内容 → 需要公司 POV、近期表现、已批准声明、已用过的例子、具体文章的证明层
    → 大量 AI 系统演示时看起来很聪明（上下文手工喂入），
      生产中崩溃（因为没人建检索层）
  Layer 3 - Source Truth（来源真相层）：
    一旦 Agent 能检索上下文，下一个问题是"信任哪个来源？"
    来源冲突实例：销售通话 vs CRM 字段 vs Slack 纠正 vs 旧 SOP vs 最新周报 vs 创始人的语音
    → 不回答这个问题，Agent 变成"格式更漂亮的自信说谎者"
    需要建立来源层级：实时真相 / 历史语境 / 灵感参考 / 永不用于公开内容 / 可影响模式但不可引用
  Layer 4 - Permissions（权限层）：
    当每个 Agent 能看到一切时，公司智能就危险了
    营销 Agent 不需要私人 HR 详情、内容 Agent 不需要客户财务数据、
    销售 Agent 不需要所有内部领导笔记
    → 需要工作流级别的权限：系统在生成答案之前就该知道这个任务被允许使用什么
    对代理商/服务公司尤其关键：客户上下文、内部上下文、潜在客户上下文、财务上下文共存
    → 不建权限边界，要么泄露要么让系统弱到无用
  Layer 5 - Feedback Loops（反馈循环层）：
    让系统复利增长的引擎
    每一次人工纠正都应该变成未来行为：
      Agent 用词生硬 → 语音规则应更新
      Agent 引用不安全例子 → 来源规则应更新
      Agent 漏掉 CRM 风险信号 → 管道扫描应更新
      Agent 把工作路由到错误位置 → 工作流规则应更新
    → 没有反馈循环 = 你在当软件的保姆
    → 有反馈循环 = 每次纠正都是整个操作系统的训练迭代
        ↓
实战数据验证（Single Grain）：
  - 500K+ token 持久记忆，90+ 每日 cron，多个专业 Agent，数千销售通话
  - 一组来源包含 2,862 个 Gong 通话 → 转化为可操作作战手册
  - 单日 15 通话 → 产出 390 洞察 + 470 事实 + 125 框架
  - 一次通话不再是通话 → 是异议库、销售培训输入、定位信号、内容创意源、CRM 风险标记、未来 Agent 指令
        ↓
实操审计：6 问快速诊断
  选一个当前浪费时间的重复工作流，回答：
    ① 依赖哪些来源？② 来源冲突时谁说了算？③ Agent 每次需要什么上下文？
    ④ 哪些上下文 Agent 永远不该看到？⑤ 哪些人工纠错反复发生？⑥ 一次纠错如何成为未来规则？
  → 答不上来 = 还没准备好自动化 → 你只会把混乱加速复制
```

### 局限与盲区

- **本文未覆盖**：五层架构的具体技术实现——Capture 层用了什么存储和索引方案、Retrieval 层的检索算法和精排策略、Source Truth 的自动化冲突解决机制（仅提到"来源层级"概念但未展开）。Feedback Loop 中"人工纠正→自动规则"的具体转换逻辑——如何从一次具体纠错中提取出可泛化的规则而不引入新错误？系统如何避免规则膨胀（持续积累导致规则相互冲突）？
- **隐含假设**：假设公司有足够规模的数据源（数千通话、CRM 记录、SOP 文档）来支撑系统的价值——对于早期创业公司（<50 人），五层架构的构建和维护成本可能超过收益。假设检索层能可靠区分为不同任务交付"正确的 6 条上下文"——实际上检索精确度在复杂任务中仍不可靠，一个错误检索可能比没有检索更糟糕。假设人工纠错的频率和质量足以驱动反馈循环——如果纠错稀疏或质量参差（有些人纠错精准，有些人随意），系统可能学到噪声。
- **可能的反例**：对于高度依赖实时外部信息的业务（如日内交易、新闻监控），公司内部知识库的价值可能被外部信号的波动性压倒——Source Truth 层定义得再好也挡不住市场三分钟翻一轮。对于创意密集型业务（如品牌策划、影视制作），过度依赖历史通话记录和 SOP 作为 Agent 语境可能强化路径依赖，压制真正新颖的解决方案。某些业务的核心知识天然不可文本化（如手工艺、表演艺术），Capture 层永远无法捕获最关键的部分。
- **商业推广偏倚**：文章末尾密集推广 Single Grain（代理服务）和 SingleBrain（产品），部分论述可能被产品叙事框架约束——五层架构恰好映射到他们的产品模块，其普适性需要独立验证。
