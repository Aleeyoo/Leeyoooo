# 内容资产工程系统

> [!tip] 💡 一句话核心主张
> 把 Agent 放进一个有规则、有状态、有边界的本地工程里，它就会从回答问题，进入建设系统。旧内容不是"储存起来"，而是被拆成可以继续调用的生产资料。

> [!important] 📌 关键结论
> - 结论1：内容资产的浪费不在存储，在于旧内容无法被再次调用——问题出在旧内容还只是"文件"而非"系统"状态。
> - 结论2：将内容拆解为问题(QST)、概念(CON)、观点(OPI)、案例(CAS)、方案(SOL)五类单元后，旧内容变成可重组、可扩展的生产资料。
> - 结论3：工程和聊天的本质区别在于：工程有规则、有状态、有目录、有版本、有来源、有后续动作，Skill 把一套跑通的方法固化成可重复执行的流程。

> [!quote] 🎬 可行动项
> - 如果你的本地文稿超过百篇，考虑用 `/dbs-content-system` skill 对自己的内容进行结构化拆解
> - 建立内容工程时先定规则层（命名、字段、关系、去重），再建状态层，最后抽取内容单元，不要一开始就"全量处理"
> - 区分"素材库"和"内容工程"：素材库只存东西，内容工程让旧内容参与新内容生产

### 论证链

```
**观点 → 论据 → 案例**

**观点1：单次任务 vs 系统工程的分野**

大多数人用 Agent 的方式是单次任务——写文案、改标题、总结文件。但真正有价值的是让 Agent 进入一个本地工程，持续建设。论证来自 dontbesilent 的实际项目：143 个目录、2330 个文件、1293 万中文字符，经过 2 天约 2 亿 token 的处理，产出 1419 个内容单元、223 个主题地图、224 个选题装配稿、1720 条显式关系。

**观点2：内容单元化是复用的前提**

一篇内容的骨架结构是：问题、概念、观点、案例、方案。将内容按这五类拆解后，新选题不必从零思考，而是从已有的问题、观点、案例和方案池中装配。

**观点3：规则先行是规模化的关键**

工程从建立新副本开始（保留回溯路径），然后依次建立规则层、状态层、内容单元库、主题地图、选题装配稿，最后补关系索引和去重候选。每个节点的关系被显式写入文件，形成可浏览、可扩展的内容关系网。
```
### 关键引述

> 素材库只是把东西存起来。内容工程会让旧内容继续参与新内容生产。

> 如果不知道哪些素材该进来，哪些素材不该进来，哪些是原始素材，哪些是处理结果，哪些是当前版本，哪些是历史痕迹，后面抽得越多，只会越乱。

> 人最应该做的是判断：这个观点对不对，这个案例够不够硬，这个结构有没有击中读者。Agent 最适合做的是把可调用的内容端出来。

### 局限与盲区

- 本文未覆盖：知识老化与版本管理（观点随时间失效如何处理？）；多作者协作场景（dontbesilent 为单人创作者，团队内容资产的冲突合并未讨论）；非中文内容的适配性。
- 隐含假设：假设用户本地已有大量文稿（百篇以上），对轻度创作者是否过度工程化未检验；假设 Agent 每次都能稳定输出同结构的单元，实际中模型波动可能导致单元质量不一致。
- 可能的反例：对于主题高度集中的创作者，五类单元可能过于细碎，批量主题地图反而增加维护负担；团队内容库中出现重复观点时，去重逻辑可能导致有价值的个性化表达被合并丢失。
