# 原始文本考古税

> [!abstract]- AI 摘要
> 企业将原始文本倒入向量数据库再用暴力检索让 AI 每次查询都"考古"——重复发现已知事实。核心边界：语义在摄入时处理，本体在检索时应用。计算是学习的天才，却是考古的废物。

---

## 扫读

> [!tip] 💡 一句话
> 把原始文本倒进向量数据库交给 AI 暴力检索，等于让模型每次查询都从零"考古"——在 Token 上支付不断重复的发现税。正确的做法是在摄入时就持久化语义关系，检索时只应用业务视角的本体解读。

> [!important] 📌 关键结论
> - 企业误解了 Sutton 的"苦涩教训"——它警告的是手工编码智能，不是保存结构化状态。停止组织数据反而让每次查询都在重新发现已知事实。
> - 原始文本让歧义变得昂贵：一个"模型"可能指 ML 模型、财务模型或活动归因模型，AI 需消耗大量 Token 来消歧。
> - 核心架构边界：语义（Semantics）在摄入时处理——持久化事实关系，不强制单一业务解释；本体（Ontology）在检索时应用——用业务视角解读已保存的语义状态。
> - Token 账单正在爆炸：单次 Claude Code 会话一天 $1,400、OpenClaw 案例 30 天 6030 亿 Token、Salesforce 今年可能花 $3 亿在 Anthropic Token 上。
> - 结构不对抗规模，它聚焦规模——遍历有组织的语义状态比暴力搜索原始数据湖更窄、更便宜、更容易验证。

> [!quote] 🎬 可行动项
> - 在数据摄入管线中应用语义标签，保存实体间的关系而非原始文本。
> - 分离语义摄入和本体应用两个阶段——不要在摄入时冻结单一业务解释。
> - 审计当前 AI 查询的 Token 消耗中有多少比例是在做"考古"（重复发现已知事实）。

## 精读

### 论证链

```
传统做法：原始文本直接倒进向量数据库
  Sutton "苦涩教训"的行业误读：
    原意 = 通用搜索+学习方法 > 手工编码智能
    误读 = "停止组织数据" → 把原始文本全部倒进去再暴力检索
        ↓
后果：每次 AI 查询都要从零"考古"
  歧义成本爆炸：一个"模型"可能是 ML 模型 / 财务模型 / 活动归因模型
    AI 需要消耗大量 Token 逐一消歧
  多跳所有权陷阱："谁应该修这个"需要预先保存关系
    无法靠实时推理解决，必须在摄入时持久化
        ↓
Token 预算危机实证：
  单次 Claude Code 会话 → $1,400/天
  OpenClaw 案例 → 6030 亿 Token/月
  Salesforce → 今年可能花 $3 亿在 Anthropic Token 上
        ↓
核心架构边界：
  语义（Semantics）→ 摄入时处理
    持久化事实关系，不强制单一业务解释
  本体（Ontology）→ 检索时应用
    用业务视角解读已保存的语义状态
        ↓
Company Brain 架构：
  状态保存一次 → 视角后续应用 → 算力花在判断上而非重复发现
        ↓
结论：结构不抵抗规模，它聚焦规模
  有组织的语义状态比暴力搜索原始数据更窄、更便宜、更可验证
```

### 关键引述


> 计算是学习的天才，却是考古的废物。
>
> 语义应在数据摄入时处理，本体应在检索时应用。持久化事实一次，之后再用业务视角解读。
>
> 错误在于把结构化状态和手工编码智能混为一谈。Company Brain 不会试图比模型更聪明，它只是让模型不必在每个问题上都支付考古税。
>
> 公司的混乱程度决定了 AI 预算。

### 局限与盲区


- 本文未覆盖：Company Brain 的具体实施方法和技术栈（仅停留在架构原则层面）；摄入时语义处理的成本与工程投入未被量化——如果每次摄入都需要人工标注，可能会成为新的瓶颈。
- 隐含假设：企业有可识别的"已知事实"需要持久化，且这些事实具有足够的稳定性和复用价值。对于高度动态或一次性使用的数据，预处理成本可能超过收益。
- 可能的反例：当检索增强生成（RAG）配合强大的 reranker 和分块策略时，原始文本+暴力检索在中小规模下可能已经足够好，架构性预处理属于过度设计。图片、视频等非文本数据类型不适用本文框架。
