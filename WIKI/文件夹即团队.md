# 文件夹即团队

> [!abstract]- AI 摘要
> "团队"不再是人的集合，而是一个文件夹——prompt 源代码加上定时器。组织设计变成文件系统设计，招人变成写 prompt，培训变成 git commit。杠杆率比写软件更高：写一次，它每天替你干活，不需要用户。

## 扫读

> [!tip] 💡 一句话
> 组织本身正在被重构——旧世界写代码、新世界写"团队"：源代码(C/Python)→Prompt源代码(.md)，编译器(GCC)→大语言模型，跑起来的进程→跑起来的Agent=团队。

> [!important] 📌 关键结论
> - "团队"的新定义：一段 prompt 源代码 + 一个定时器，跑起来叫团队，停下来回到磁盘只是文件夹。市场团队、工程团队、PM团队都可以是文件夹
> - 杠杆率三层：写软件杠杆（写一次N个用户用）< 写团队杠杆（写一次每天替你干活不需要用户） < 组织杠杆（多个文件夹团队协作形成可生产环境运行的组织）
> - 组织管理三重构：组织设计→文件系统设计（目录怎么组织、什么定时任务串起来）；招人→写prompt（先写文件夹验证再考虑补真人）；培训→git commit（不满意改两行commit，下次运行就是新版本）
> - 真正可用的"组织"需要三层：PM团队（需求审核过滤） + 工程团队（执行） + 客服/数据团队（闭环反馈），全部是文件夹
> - 未来五年最有杠杆的技能：会写"团队级别的 prompt"——不是写一句话让 ChatGPT 回答，而是把一份工作写成文件夹里若干 .md、组织好关系、加上定时任务和 hook

> [!quote] 🎬 可行动项
> - 识别当前工作中哪一块"团队"可以被悄悄变成一个文件夹——先写一个文件夹试试，跑出来的结果真的有人用再考虑补真人监管
> - 审视自己的工作目录结构：目录组织是否反映了实际业务逻辑？是否可以用定时任务串联多个"虚拟部门"
> - 将团队不满意的地方视为"需要改两行 .md commit"的问题，而不是"需要开会谈话"的问题

### 关键引述

> 我那个市场团队，写它大概花了我半个下午。然后它每天早上 6 点准时起床，开始干一些原本得我自己起床做的活：扫信息、发小红书、发 Twitter、发 Facebook……每一次它运行，我都不在场。

> 你以前问"我的公司怎么组织"，答案是组织架构图、汇报关系、职级序列。今天问"我的公司怎么组织"，答案可能是"我的目录怎么组织、哪些文件夹放什么、用什么定时任务串起来"。

> 我对一个"团队"不满意了——比如它发的小红书风格不对、用词太营销腔——我不用开会、不用一对一谈话、不用写 PIP。我直接打开它的 .md，改两行，commit。下次它再跑，就是新版本。

> 未来五年最有杠杆的一项技能，我觉得是——会写"团队级别的 prompt"。把一份要做的事，写成一个文件夹里的若干 .md，组织好它们的关系，加上定时任务和 hook，让它稳定地、可重复地、可传承地替你工作。然后这个文件夹里的"人"，永远不离职，永远不抱怨，永远不要 head count，永远在跑。

### 局限与盲区

- 本文未覆盖：没有讨论什么类型的工作不能 agent 化（如需要真实人际信任、肢体接触、法律签章的岗位）；没有涉及虚拟团队协作时的隐性知识传递成本——真人团队的自然沟通不需要显式写入 .md 文件，但虚拟团队需要把所有隐性知识显式化；没有讨论系统出错时的责任归属和风险控制
- 隐含假设：假设所有工作都可以被拆解为定时任务（但许多创造性、策略性工作需要灵感和语境判断而非固定节奏）；假设"半下午写完"的团队产出质量可与真人团队相当但未提供对比；假设工具稳定性足够支撑生产环境运行
- 可能的反例：高度监管行业（金融合规、医疗诊断）的 Agent 自主行动可能引入法律风险；"文件夹团队"在需要跨团队谈判、利益协调等复杂人际交互场景时不适用；如果 prompt 本身有隐蔽偏见或错误，git commit 式修改可能积累不可追溯的错误链
