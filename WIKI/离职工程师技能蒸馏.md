# 离职工程师技能蒸馏

> [!tip] 💡 一句话核心主张
> dot-skill 把离职工程师的评审标准和故障启发式转化为可编辑、可版本化的 SKILL.md 文件，但真正可靠的路径是只取 work.md（能力），暂时放弃 persona.md（人格），因为行为保真度至今无人能测量。

> [!important] 📌 关键结论
> - COLLEAGUE.SKILL 的本质是文件格式标准而非人格克隆：它无法证明生成的技能能捕捉真实工程师的判断力，论文自身将此列为"行为保真度前沿"这一开放问题。
> - 能力与人格分离是该项目最精妙的设计决策：work.md 持有评审准则和决策启发式，persona.md 持有个性标签驱动的行为规则，前者可信任，后者可能是"偏见被编译进行为"。
> - 纯文本纠错和版本回滚赋予用户控制权：用自然语言告诉 Agent"他不会在这里 push back"，系统自动修正对应章节并归档旧版本，支持回退到最近10个版本中的任意一个。

> [!quote] 🎬 可行动项
> - 优先采用 work-only 路径（`/{character}-{slug}-work`），用已有的带评分的代码评审结果来验证 work.md 的输出质量，再考虑启用完整技能。
> - 在生成阶段使用 `--no-install-claude-skill` 标志暂停自动安装，先逐条阅读 work.md 和 persona.md 中每条规则，防止人格标签被意外编译为规则。
> - 将退出的同事的评审 checklist 封装为 work.md 技能，检查项按 paper 示例排序：认证→输入验证→频率限制→响应格式→敏感数据暴露→其他小问题。

### 论证链

```
**观点：专家判断力散落在碎片化的痕迹中，需要一个可操作的萃取格式**

专业知识从不活在手册里——它分散在设计文档、代码评审评论、聊天决策和故障记录中。当工程师离职时，这些隐性知识随之流失。dot-skill 的核心命题是：能否在人员离开前，将这些碎片转化为 Agent 可加载的技能文件？
```
### 核心设计：S = (A, M, L) 契约

论文将该方法命名为"person-grounded trace-to-skill distillation"。生成的文件包遵循 S = (A, M, L) 模型：A（Artifacts，七个生成文件，遵循 schema v3）、M（Manifest，安装元数据）、L（Lifecycle，版本号、纠错计数、回滚历史）。这套契约使技能包具备五个特性：可移植、可检查、可组合、可纠错、可治理。

### 文件结构与三大入口

生成器输出七个文件：SKILL.md（主入口）、work.md（能力）、persona.md（人格）、work_skill.md 和 persona_skill.md（两个子技能入口）、manifest.json 和 meta.json（元数据）。基于此产生三个加载入口：完整技能、仅工作、仅人格。work-only 是推荐的安全路径，因为评审清单不需要人格也能工作。

### 纠错回滚与版本管理

纠错用自然语言完成。对工作内容的修正（如"他不应该在那个地方 push back"）会匹配并修补 work.md 中对应的 ## 章节；对行为的修正以 {scene, wrong, correct} 三元组追加到 persona.md 的纠错日志。每次更新自动归档旧版本，version_manager.py 支持回退到最近10个版本中的任意一个。

### 人格层的隐忧：标签直接编译为规则

人格分析器将自由文本标签（如 "blame-shifter"、"PUA"）翻译为 Layer 0 行为规则——Agent 绝对不能违反的硬约束。手动输入的标签权重高于从实际痕迹中提取的行为模式。repo 自己的同事演示中，技能在提示下熟练地推卸责任，说明偏差可以通过设计被编译进行为。

### 保真度鸿沟与治理空白

论文证明了一个文件格式和工作流的存在性与可运行性，但未证明生成技能能复现真实工程师的判断。没有留出测试集评估。治理方面：本地优先、可版本化赋予用户控制权，但代码层面没有任何机制强制同意、保留期或数据删除——删除只是 `rm -rf`。产品页面提到 RAG，但 repo 的 requirements.txt 中没有检索运行时依赖。

## 局限与盲区

- **未覆盖方面**：论文和文章均未涉及持续学习或技能衰减——离职工程师的技能是静态快照，不会随技术演进而更新。也未讨论多人技能合并：当一个团队多人离职时，如何融合而非简单叠加多个 SKILL.md。关系（relationship）和名人（celebrity）两种预设的论文尚未发布，这两个场景下的知情同意问题更棘手。
- **隐含假设**：假设流失工程师的工作痕迹是可访问的、且足以代表其判断力——当工程师在聊天中做了大量口头决策而文档很少时，萃取基底薄弱。假设 Markdown 文件格式能承载工程判断——判断力是否可文本化本身就是开放问题。
- **可能的反例**：评估过硬的 engineers 可能因其评审工作在公开 PR 中已被团队吸收，生成其 skill 的边际收益很小。初级工程师的输出痕迹更多反映的是"被纠正"过程而非成熟判断力，萃取可能放大错误模式。
- **伦理问题**：尽管产品页面提到 consent，代码中没有强制同意机制。同事是否知道自己的痕迹正在被采集和封装？离职后 skill 的合规使用期限由谁决定？
