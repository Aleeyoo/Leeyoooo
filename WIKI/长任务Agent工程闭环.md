# 长任务Agent工程闭环

> [!abstract]- AI 摘要
> 提出长任务 Agent 在工程化落地时的三个核心问题（状态丢失、规划失真、验证失灵）和五层架构解决方案（状态层、规划层、执行层、验证层、监督层），强调 Agent 的上限看模型但下限看架构。

---

## 扫读

> [!tip] 💡 一句话
> 长任务 Agent 进生产不能只靠更聪明的 prompt，需要在模型外围补三层控制（Context 管现场、Planning 管边界、Verification 管证据），加上执行层和监督层构成五层可恢复、可验证、可停止的工程系统。

> [!important] 📌 关键结论
> - 长任务 Agent 最常见的失控链路：上下文越来越脏→计划越来越虚→验证越来越浅，Agent 没有突然变笨，只是在缺少控制回路的系统里越跑越偏
> - Agent 最危险的能力是把没做对的事讲得像做完了——curl-only verification、stub 逃逸、自我评分过高是三大典型陷阱
> - 更强模型会改变 harness 的设计但不会取消 harness——外部状态、外部验证、权限责任和成本控制这四类东西很难被模型能力完全吃掉

> [!quote] 🎬 可行动项
> - 每个长任务 Agent 系统先补上 6 个模式：spec-first（先写施工单）、plan gate（计划先过审）、progress ledger（每阶段写状态）、independent evaluator（独立验收）、stop condition（硬停止条件）、rollback path（可回滚）
> - 判断一个 Agent 工作流先跳过模型名，直接问五个问题：状态在哪、计划怎么拆、执行怎么记录、结果怎么验证、什么时候必须停

## 精读

### 论证链

```
长任务Agent三类失控
      ↓
状态丢失 → context window像工作台越堆越乱，session间断裂
      ↓
规划失真 → Agent缺乏任务尺寸感，倾向one-shot完整项目或过早判断"够了"
      ↓
验证失灵 → curl-only verification/stub逃逸/自我评分过高，把浅验证包装成完成
      ↓
五层架构解法：
1.状态层：progress.md/task ledger/trace log外部持久化
2.规划层：任务切分+运行预算(token/time/tool call上限)
3.执行层：每次工具调用回到任务状态里
4.验证层：机器验证+环境验证+独立评价器(必须有权判FAIL)
5.监督层：权限/预算/危险操作确认/失败升级/回滚
      ↓
更强模型会改变但不会取消harness——外部状态/外部验证/权限/成本无法被模型能力吃掉
      ↓
结论：Agent上限看模型，下限看架构；未来Agent更像可审计的工程系统
```

### 关键引述

> 生产级 Agent 最该警惕的，是系统误判成功。失败可以重试，可以回滚，可以升级给人。真正贵的是：它失败了，系统却以为它成功了。

> Agent 的质量不只来自生成，还来自行动后的反馈。缺状态，反馈留不住。缺规划，反馈不知道该回到哪个阶段。缺验证，反馈本身就是假的。

> 好的 Agent 架构应该随着模型能力变化而变薄，把不再需要的外壳拆掉，把真正有价值的控制点留下来。
