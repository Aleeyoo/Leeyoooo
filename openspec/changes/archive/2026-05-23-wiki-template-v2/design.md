## Context

当前 WIKI 模板为初级版本（`Library/temples/WIKI.md`），结构为 flat frontmatter + 摘要 + 要点 + 内容 + 关联。模板作为"复述工具"工作正常，但无法支撑 WIKI 作为"知识资产"的长期价值。探索阶段确定了三层升级方向：人扫读、人深读、AI 检索。

`Library/temples/type-project.md` 与 `openspec/specs/knowledge-pipeline.md` 已存在，需要同步更新。

## Goals / Non-Goals

**Goals:**
- WIKI 模板支持 AI 检索索引（`concepts`）和可信度标注（`confidence`）
- 正文分为扫读区（快速判断是否值得读）和精读区（深入理解）
- 引入"局限/盲区"区块，要求 AI 批判性思考而非简单复述
- 项目模板移除冗余的关联 WIKI 正文区块（`.base` 视图已覆盖）
- 工作流规范反映上述改动
- 用真实文章首次跑通全流程

**Non-Goals:**
- 不改动 `.base` 文件格式
- 不改动命名规范
- 不改动用户交互模型（自动处理 + 图片末尾提议）

## Decisions

### 1. 扫读区 vs 精读区的边界

**决定**: 扫读区 = 一句话核心主张 + ≤3 条关键结论 + 可行动项（如有）。精读区 = 论证链 + 关键引述 + 局限盲区。

**理由**: 扫读区解决"要不要看"（5秒决策），精读区解决"看了能获得什么"（深入理解）。边界清晰，AI 生成时有明确的分段指令。

**备选**: 折叠 callout 嵌套。拒绝——Obsidian 折叠在 .base 视图里可能不兼容。

### 2. confidence 字段的三级分类

**决定**: `high`（事实/一手资料）、`medium`（有逻辑支撑的观点）、`low`（推测/预测需验证）。

**理由**: 三级够用不过度。读者和未来 AI agent 需要区分"这 WIKI 在陈述什么类型的信息"。

### 3. concepts 字段 vs 只用 tags

**决定**: 两个字段并存。`tags` 用于人类分类导航，`concepts` 用于 AI 语义检索。`concepts` 是自由文本数组，不限于预设标签体系。

**理由**: tags 受限于项目命名空间，concepts 可以横跨项目，做跨领域知识发现。

### 4. 多项目归属：共享式而非分裂式

**决定**: 一篇 WIKI 可以 Belongs to 多个项目（用 YAML 数组），不做内容拆分。每个项目的 `.base` 通过 `hasLink` 自然收录。

**理由**: 避免内容重复和维护负担。`.base` 视图层天然支持多归属。

## Risks / Trade-offs

- **模板复杂度增加** → AI agent 需要更多上下文来正确填充。缓解：工作流规范中提供详细字段说明和示例。
- **concepts 可能被滥用** → 如果 AI 随意填充会污染检索。缓解：规范中要求 concepts 必须是"本文核心讨论的独立概念"，限制 3-8 个。
- **confidence 主观性** → 不同 AI 对不同内容的可信度判断可能不一致。缓解：三级简化分级，每级有明确判断标准。
